# 逆解析の証拠からコードへ：spec ゲート

[English](spec-workflow.en.md) ｜ **日本語** ｜ [繁體中文](spec-workflow.md)

この repo には知識ベースと実装が同居している。その間には関門が必要だ。さもないと
「コードを読んだときの印象」がそのままコードになり、3 か月後には誰もその印象の根拠を
覚えていない。

## 3 つの状態

```
逆解析の証拠  ──►  DRAFT spec  ──►  証拠レビュー  ──►  READY spec  ──►  実装  ──►  同状態での検証  ──►  CONFORMED spec
```

| 状態 | 意味 | 何が許されるか |
|---|---|---|
| `DRAFT` | 逆アセンブルやマニュアルから書き起こした規格。まだ一条ずつ証拠が付いていない | 実験的なコードのみ。本線には入れない |
| `READY` | すべての言明に出典がある（ファイル・オフセット、マニュアルの頁、または再実装独自と明記） | **正式な実装を書いてよい** |
| `CONFORMED` | 実装済みで、オリジナルと同じ状態で検証済み | 他の spec が前提として引用してよい |

**正式な実装を許すのは `READY` だけ。** これがこの流れの要点であり、
「そう思う」と「調べた」を分ける。

## spec に何を書くか

各 spec は `docs/30-remake/specs/` に置き、冒頭に状態と範囲、本文に言明を一条ずつ、
各条の後ろに出典を記す。出典は 3 種類しかない：

- **オリジナルの証拠**：ファイル・オフセットとバイト、またはマニュアルの頁。
- **推論**：どのオリジナル証拠から導いたか。推論の手順も書く。
- **再実装独自**：オリジナルはそうしていない。この再実装自身の決定である。

3 番目は特に明記し、さらに 2 つに分ける：

- **意図的な非準拠**（例：セグメントの追い出しをやらない）——オリジナルにはその挙動があり、
  こちらが採らないと決めたもの。
- **再実装自身のもの**（例：デバッグ出力の形式）——オリジナルに対応物が無いもの。

両者を混ぜると「ここがオリジナルと違うのはバグか設計か」に答えられなくなる。

## 検証は「同じ状態」で

`CONFORMED` の敷居は「テストした」ではなく、**オリジナルと同じ状態で突き合わせた**こと。
同じ codefile、同じ入力、同じ初期スタックで、両者が同じものを出す。

近似した入力で突き合わせれば、合格に見えて何も証明しない結果が得られる。詳細は
[実現可能性の評価](feasibility.ja.md)の oracle 環を参照。

## ラベルは期限切れになる

`再実装独自` のようなラベルは**その時点の決定**であって、永久の事実ではない。
オリジナルの証拠があとから解ければ、「独自」と付けたものに実は対応物があったと
わかることもある。だから各 spec には日付を記し、既存の言明を覆すときは：

- 本文は正しい現況に書き直し、どう間違えたかを本文で語らない。
- 覆した記録は 1 か所、`PLAN.md` の正誤表にまとめる。
- 教訓は規則として書き、出来事として書かない——現在形の教訓は、直った瞬間に偽の言明になる。
