# Go で p-machine を作り直す：実現可能性の評価

[English](feasibility.en.md) ｜ **日本語** ｜ [繁體中文](feasibility.md)

この評価はひとつの具体的な問いに答える——**手元の証拠は、1984 年 DOS 版 p-system を
走らせる Go 製インタプリタを支えるに足りるか？**

結論から言う。**中核インタプリタは作れる。しかもそれが全体で最も確信のある部分であり、
危険は命令セットではなく標準手続きと I/O に集中している。** 決め手は、この仕事に
oracle があることだ——オリジナルのインタプリタもオリジナルのディスクも手元にあり、
突き合わせて走らせられる。

> 関連：[spec ゲート](spec-workflow.ja.md)｜
> [256 エントリ対照表](../10-interpreter/opcode-map.ja.md)

## 6 つの層を 1 層ずつ

| 層 | 必要なもの | 手元の証拠 | 判断 |
|---|---|---|---|
| 1 命令実行 | 256 枠の意味、スタック模型、活動記録の版面 | IV.0 マニュアルの逐条記述、8086 版 169 本すべての逆アセンブル、68000 版による相互照合 | **作れる** |
| 2 codefile 形式 | セグメント辞書、セグメント・ヘッダ、手続き辞書、定数プール、ジャンプ表 | マニュアル第 2 章、8086 版から読み取ったヘッダ 3 フィールドの実オフセット | **作れる。もう一巡の解読が要る** |
| 3 標準手続き（CSP） | 各本の引数と挙動 | 33 本はインタプリタ内に機械語で埋め込み。残りは `SYSTEM.PASCAL` の中 | **最大の未知** |
| 4 I/O とファイルシステム | unit の読み書き、画面、キーボード、`.VOL` ディレクトリ | マニュアルの三層 I/O の抄訳、`.VOL` 形式は実装済み | **量は多いが機械的** |
| 5 メモリ管理 | Codepool、セグメントの出し入れ、`Ref_Count`／`Activity` | 切り替えのコードは解読済み | **再実装ではやらなくてよい** |
| 6 浮動小数点 | 8 バイト実数のビット形式と四則 | 専用ルーチン 16 本。形式は IEEE 754 binary64 と判明 | **作れる** |

第 5 層には一言要る。オリジナルがセグメントをメモリから追い出すのは、1984 年の機械に
全部が載らなかったからだ。Go 版にその制約は無く、全セグメントを常駐させられる。
**これは意図的な非準拠であって、未着手ではない**——この差は spec に書いておかないと、
3 か月後には誰も区別がつかなくなる。

## なぜ中核の命令セットがいちばん確実なのか

独立した 3 つの出典が互いを裏づける：

1. **IV.0 公式マニュアル**が意味とスタック効果を一条ずつ書いている。
2. **8086 版インタプリタ**の 169 本はすべて逆アセンブル済みで、命令数の中央値は 8——
   端から端まで読み切れる短さだ。
3. **68000 版インタプリタ**（1985 年 SunDog）は同一バージョンの別移植で、98 本を
   一条ずつ検証済み。同じ命令の 2 つの命令セット上の 2 通りの書き方は、互いの検算になる。

さらに **UCSD Pascal I.5 のソースは公開されている**——PDP-11 版インタプリタと OS の
ソースを含む。版は古いが多くの命令の意味は変わっておらず、第 4 の出典として使える。

3 つの実装と 1 冊のマニュアルが同じ意味を指すとき、間違える余地はほとんど残らない。

## oracle があってはじめて制御可能になる

差分テストの完全な環は出来合いである：

```
Pascal ソース
   │  psys21 の SYSTEM.COMPILER（DOSBox 内で実行）
   ▼
codefile（p-code）
   ├─────────────────────► オリジナルの SYSTEM.PME.86（DOSBox）──► 出力 A
   └─────────────────────► Go 版 p-machine ────────────────────► 出力 B
                                                       A と B を比較
```

これが買うもの——**「この命令の理解が間違っている」が、3 か月後に発覚するずれではなく、
落ちるテストになる。** oracle の無い再実装は、コードを読んだ者の確信に頼るしかない。
oracle があれば、確信を信号に変えられる。

代償は、まず DOSBox 内で psys21 を走らせ、入力を送り出力を取れるようにすること。
これ自体が未経験なので、最初のマイルストーンの前提条件として挙げてある。

## 段階

| マイルストーン | 成果物 | 合格の基準 |
|---|---|---|
| **M0** | codefile リーダ | `SYSTEM.PASCAL` に対してセグメント名と手続き辞書を出力し、マニュアルの定義と一致し自己整合する |
| **M1** | 純計算部分集合のインタプリタ | 手書きの p-code 列で、Go 版と DOSBox 上のオリジナルが同じ出力を出す |
| **M2** | 複数セグメント呼び出しと一部の CSP | `SYSTEM.COMPILER` でコンパイルした小さなプログラムが走り切る |
| **M3** | `SYSTEM.PASCAL` が動く | プロンプトが出て、コマンドを 1 つ受け付ける |

M0 は完全に静的で未知は無い。M1 は oracle が整っている必要がある。M2 で第 3 層に触れ始め、
作業量は小さなプログラムが実際に何本の CSP を使うかで決まる。M3 は「本当に動くのか」への
答えであり、到達する前に宣言してはならない。

4 つのマイルストーンはすべて到達済みである。M3 の実際の結果はここに書いた基準より
一歩先を行った——プロンプトが出るだけでなく、Filer に入ってディレクトリを一覧でき、
起動全体の 226,623 条の p-code がオリジナルと一条ずつ一致する
（[自己起動](specs/03-boot.ja.md)参照）。

## 障害になるとわかっているもの

- **マニュアルは IV.0、ディスクは IV.2.1。** 両者の opcode 番号は枠ごとに照合済みだが、
  意味が一条ずつ同じであることは未検証で、割り当てが違う枠が 1 つ既に見つかっている
  （`0xff`）。マニュアルだけが支持しインタプリタの裏づけが無い意味は、
  すべて仮定として扱う必要がある。
- **`SYSTEM.PASCAL` にソースは無い。** IV.x の OS は黒箱にしかならない。M3 で詰まったら、
  デバッグは oracle との突き合わせに頼るしかなく、ソースを読むことはできない。
- **埋め込み機械語の 33 本**は 1 本ずつ意味を読み出すしかなく、近道は無い。
  それらは `SYSTEM.PASCAL` が直接依存しているものだ。
- **実数形式は当時未解だった。** のちに @0x22a8 のヘルパから IEEE 754 binary64 と解読された
  （マニュアルの BCD という記述はこの版には当てはまらない）。四則と比較はすべて
  突き合わせ済みである。

## この判断はどこで外れうるか

いちばん過大評価しやすいのは第 3 層だ。「33 本」は表を数えた数字だが、それはセグメント 1 で
**埋め込み実装を持つ**ものだけである。`SYSTEM.PASCAL` がほかに何本の CSP を使うかは、
実際にプログラムをコンパイルして参照を見るまでは推測にすぎない。

いちばん過小評価しやすいのは M2 と M3 のあいだの距離である。OS が使うもの——
タスク切り替え、segment fault、割り込み、時計——は、小さなプログラムには 1 本も現れない。
