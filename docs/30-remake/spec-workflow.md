# 從逆向證據到程式碼：spec 閘門

這個 repo 同時放知識庫與實作。兩者之間需要一道閘門，否則「我讀碼時的印象」
會直接變成程式碼，而三個月後沒有人記得那個印象的依據是什麼。

## 三個狀態

```
逆向證據  ──►  DRAFT spec  ──►  證據審查  ──►  READY spec  ──►  實作  ──►  同狀態驗證  ──►  CONFORMED spec
```

| 狀態 | 意思 | 能做什麼 |
|---|---|---|
| `DRAFT` | 從反組譯或手冊寫下來的規格，還沒有逐條配上證據 | 只能寫實驗性的碼，不進主線 |
| `READY` | 每一條斷言都有出處（檔案偏移、手冊頁碼、或標明是 remake 自訂） | **可以照著寫正式實作** |
| `CONFORMED` | 實作完成，而且在與原版相同的狀態下驗證過 | 可以被其他 spec 引用當前提 |

**只有 `READY` 授權正式實作。** 這一條是整個流程的重點：
它把「我以為」和「我查過」分開。

## spec 要寫什麼

每份 spec 放在 `docs/30-remake/specs/`，開頭是狀態與範圍，本文逐條寫斷言，
每一條後面標出處。出處只有三種：

- **原版證據**：檔案偏移加位元組，或手冊頁碼。
- **推論**：從哪幾條原版證據推出來的，推論的步驟要寫。
- **remake 自訂**：原版沒有這樣做，是這個 remake 自己的決定。

第三種要特別寫清楚，而且要分成兩類：

- **刻意不照做**（例如不做段換出）——原版有這個行為，我們決定不要。
- **remake 自己的東西**（例如除錯輸出格式）——原版沒有對應物。

兩者混在一起就沒辦法回答「這裡與原版不一樣，是 bug 還是設計」。

## 驗證要在「同一個狀態」

`CONFORMED` 的門檻不是「測試過了」，是**在與原版相同的狀態下比對過**。
同一份 codefile、同一組輸入、同一個起始堆疊，兩邊跑出同樣的東西。

用近似的輸入去比對，會得到一個看起來通過、實際上什麼都沒證明的結果。
細節見[可行性評估](feasibility.md)裡的 oracle 迴路。

## 標籤會過期

`remake 自訂` 這種標籤是**當下的決定**，不是永久事實。
原版證據後來被解出來之後，原本標成「自訂」的東西可能其實有對應物。
所以每份 spec 要記日期，而且推翻既有斷言時：

- 正文改寫成正確的現況，不在正文敘述當初怎麼錯的；
- 推翻紀錄集中到 `PLAN.md` 的勘誤表一處；
- 教訓寫成規則，不寫成事件——現在式的教訓會在修好那一刻變成假斷言。
