# 用 Go 重做一台 p-machine：可行性評估

這份評估回答一個具體的問題：**手上現有的證據，夠不夠支撐一個能跑 1984 年
DOS 版 p-system 的 Go 直譯器？**

結論先講：**核心直譯器可以做，而且是整件事裡最有把握的部分；
風險集中在標準程序與 I/O，不在指令集。** 決定性的因素是這件事有 oracle——
原版直譯器與原版磁碟都在手上，可以拿來對拍。

> 延伸閱讀：[spec 閘門流程](spec-workflow.md)｜[256 格對照表](../10-interpreter/opcode-map.md)

## 六層，逐層盤點

| 層 | 需要什麼 | 現有證據 | 判斷 |
|---|---|---|---|
| 1 指令執行 | 256 格語意、堆疊模型、活動記錄版面 | IV.0 手冊逐條語意；8086 版 169 支常式全部反組譯；68000 版可交叉對照 | **可做** |
| 2 codefile 格式 | segment dictionary、段表頭、程序字典、常數池、jump table | 手冊第二章；8086 版讀到段表頭三個欄位的實際偏移 | **可做，要再解一輪** |
| 3 標準程序（CSP） | 每一支的參數與行為 | 33 支內嵌在直譯器裡的機器碼；其餘在 `SYSTEM.PASCAL` 裡 | **最大未知** |
| 4 I/O 與檔案系統 | unit 讀寫、螢幕、鍵盤、`.VOL` 目錄 | 手冊三層 I/O 的摘譯；`.VOL` 格式已實作 | **工作量大但機械性** |
| 5 記憶體管理 | Codepool、段換入換出、`Ref_Count`／`Activity` | 切段那段碼已解 | **remake 可以不做** |
| 6 浮點 | 8 位元組實數的位元格式與四則 | 16 支專屬常式，`MPR`／`DVR` 尚未讀完 | **可延後** |

第 5 層值得特別說。原版把段換出記憶體，是因為 1984 年的機器裝不下；
Go 版沒有這個約束，可以把所有段常駐。**這是刻意不照做，不是還沒做**——
差別要寫進 spec，否則三個月後沒有人分得出來。

## 為什麼核心指令集是最有把握的部分

三個獨立來源互相印證：

1. **IV.0 官方手冊**逐條寫了語意與堆疊效應。
2. **8086 版直譯器**的 169 支常式已經全部反組譯，指令數中位數 8，
   短到可以逐條讀完。
3. **68000 版直譯器**（1985 年 SunDog）是同一版的另一個移植，
   已經逐條驗過 98 支。同一條指令在兩個指令集上的兩種寫法，
   互相就是對方的檢查。

再加上 **UCSD Pascal I.5 的原始碼是公開的**——含 PDP-11 版直譯器與作業系統原始碼。
版本比較舊，但很多指令的語意沒有變，可以當第四個來源。

三份實作加一份手冊都指向同一個語意時，猜錯的空間很小。

## 有 oracle，這件事才算可控

差分測試的完整迴路現成：

```
Pascal 原始碼
   │  psys21 的 SYSTEM.COMPILER（在 DOSBox 裡跑）
   ▼
codefile（p-code）
   ├─────────────────────► 原版 SYSTEM.PME.86（DOSBox）──► 輸出 A
   └─────────────────────► Go 版 p-machine ─────────────► 輸出 B
                                              比對 A、B
```

意義在於：**「我對這條指令的理解是錯的」會變成一個會失敗的測試，
而不是三個月後才發現的偏差。** 沒有 oracle 的 remake 只能靠讀碼的信心，
有 oracle 就能把信心換成訊號。

代價是要先讓 DOSBox 裡的 psys21 跑起來，並且能自動送輸入、取輸出。
這件事本身沒做過，列為第一個里程碑的前置。

## 分階段

| 里程碑 | 交付 | 怎麼算通過 |
|---|---|---|
| **M0** | codefile 讀取器 | 對 `SYSTEM.PASCAL` 跑出段名與程序字典，與手冊定義一致且自洽 |
| **M1** | 純計算子集的直譯器 | 手寫 p-code 序列，Go 版與原版在 DOSBox 上輸出相同 |
| **M2** | 多段呼叫與部分 CSP | 用 `SYSTEM.COMPILER` 編出來的小程式能跑完 |
| **M3** | 跑得動 `SYSTEM.PASCAL` | 出現提示符並能接受一個指令 |

M0 完全靜態，沒有任何未知；M1 需要 oracle 就位；M2 開始碰第 3 層，
工作量取決於一個小程式實際會用到幾支 CSP；M3 是「能不能真的跑起來」的答案，
在到達之前不應該宣稱。

## 已知會擋路的地方

- **手冊是 IV.0，磁碟是 IV.2.1。** 兩者的 opcode 編號已經逐格對過，
  但語意逐條相同沒有驗證，而且已經找到一格分配不同（`0xff`）。
  凡是只有手冊支持、沒有直譯器佐證的語意，都要當成假設。
- **`SYSTEM.PASCAL` 沒有原始碼。** IV.x 的作業系統只能黑箱。
  如果 M3 卡住，除錯只能靠 oracle 對拍，不能讀原始碼。
- **33 支內嵌機器碼程序**必須逐支讀出語意，沒有捷徑。
  它們是 `SYSTEM.PASCAL` 直接依賴的東西。
- **實數格式未解。** 已知是 8 個位元組、符號位在最高位元組。
  在浮點運算出現之前不擋路，出現之後就會擋。

## 這個判斷可能錯在哪

最容易高估的是第 3 層。「33 支」是數表格數出來的，但那只是 segment 1 裡
**有內嵌實作**的那些；`SYSTEM.PASCAL` 還會用到多少支別的 CSP，
在真的編一個程式出來看它引用什麼之前，只是推測。

最容易低估的是 M3 與 M2 之間的距離。作業系統會用到的東西
（task switch、segment fault、中斷、時鐘）在小程式裡一支都不會出現。
