## 1. ファイルのブロック分け

1.1 codefile は 512 バイトのブロック単位。セグメントのコードは必ずブロック境界から始まる。
**[マニュアル p.30]**

1.2 ブロック 0 はセグメント辞書の最初のレコード。**[マニュアル p.27]**

## 2. セグメント辞書レコード（512 バイト）

2.1 1 レコードは最大 16 セグメントを記述し、あるセグメントの情報は 6 本の並行配列に
分かれて、同じ添字で引かれる。**[マニュアル p.27]**

2.2 レコードのバイト版面（p.28–29 の Pascal 宣言から欄ごとに算出。合計はちょうど 512）：

| バイト | 欄 | 1 項の大きさ |
|---|---|---|
| `0x000`–`0x03f` | `Disk_Info[16]`：`Code_Addr`（開始ブロック）、`Code_Leng`（ワード数） | 4 |
| `0x040`–`0x0bf` | `Seg_Name[16]`：8 文字、未使用は空白で埋める | 8 |
| `0x0c0`–`0x0df` | `Seg_Misc[16]` | 2 |
| `0x0e0`–`0x0ff` | `Seg_Text[16]`：interface text の開始ブロック | 2 |
| `0x100`–`0x11f` | `Seg_Info[16]` | 2 |
| `0x120`–`0x19f` | `Seg_Famly[16]` | 8 |
| `0x1a0`–`0x1a1` | `Next_Dict`：次レコードのブロック番号。0 なら無し | 2 |
| `0x1a2`–`0x1af` | 予約 7 ワード | — |
| `0x1b0`–`0x1fd` | `Copy_Note`：`string[77]`（長さバイトに文字が続く） | — |
| `0x1fe`–`0x1ff` | `Sex`：常に 1 | 2 |

**[マニュアル p.28–32]**、版面は宣言から算出。
**[標本]** `Copy_Note` は
`"Copyright 1979 U.C. Regents; Copyright 1985 SofTech Microsystems"`、`Sex` は 1 と読める。
レコード末尾の 2 欄がどちらも合うということは、あいだの全欄の大きさの合計が正しいことを意味する。

2.3 `Code_Leng` は 16 ビット・ワード数で、**relocation list を含み、
segment reference list を含まない**。**[マニュアル p.30]**

2.4 辞書は連結リストで、後続レコードは 1 ブロックずつ、code segment のあいだに挟まる。
**[マニュアル p.27]**
**[標本]** `SYSTEM.PASCAL` には 2 件——ブロック 0（16 項）とブロック 133（12 項）、
合計 28 セグメント。

2.5 `Seg_Misc` のビット配置（`Seg_Type` 3 ビット、`Filler` 5 ビット、`Has_Link_Info` 1 ビット、
`Relocatable` 1 ビット、宣言順に下位から上位へ）：

| bit | 欄 |
|---|---|
| 0–2 | `Seg_Type`：0 `No_Seg`、1 `Prog_Seg`、2 `Unit_Seg`、3 `Proc_Seg`、4 `Seprt_Seg` |
| 3–7 | `Filler` |
| 8 | `Has_Link_Info` |
| 9 | `Relocatable` |

宣言順は **[マニュアル p.28]**。「下位から上位へ」は 2.6 の `Seg_Info` が独立に確認する。
**[標本]** 下位 3 ビットは `Unit_Seg` または `Proc_Seg` と読め、2.7 で `Seg_Famly` から
判定した型と完全に一致する。

> ⚠ **bit 8 と bit 9 の意味は未検証。** 標本の 28 セグメントで `Seg_Misc` は `0x0202` と
> `0x0203` の 2 値しか取らず、bit 9 は常に 1、bit 8 は常に 0——**変異が無ければ識別力も無い**。
> しかも 28 セグメントの relocation list ポインタはすべて 0 で、
> 「bit 9 = `Relocatable`」とはうまく噛み合わない。実装は宣言順に解釈するが、
> この 2 ビットに依存した判断は一切行わない。

2.6 `Seg_Info` のビット配置（合計ちょうど 16 ビット）：

| bit | 欄 |
|---|---|
| 0–7 | `Seg_Num`：ローカルなセグメント番号 |
| 8–11 | `M_Type`：0 `M_Psuedo`、2 `M_PDP_11`、3 `M_8080`、9 `M_8086`、11 `M_68000` … |
| 12 | `Filler` |
| 13–15 | `Major_Version`：4 = `IV` |

**[マニュアル p.28]**。
**[標本]** `KERNEL` は `0x8001` と読め、`Seg_Num` 1、`M_Type` `M_Psuedo`、版 `IV`。
上位から下位へ配置すると `Seg_Num` は 1 ではなく 128 になる——**この 1 項が同時に
宣言全体の packed record の詰め方向を確定させる**。2.5 はこの結論に依存している。

2.7 `Seg_Famly` は変種レコード。`Prog_Seg`／`Unit_Seg` は 4 つの整数
（`Data_Size`、`Seg_Refs`、`Max_Seg_Num`、`Text_Size`）、
`Proc_Seg`／`Seprt_Seg` は外側の program／unit の 8 文字名。**[マニュアル p.29]**
**[標本]** `ASSOCQUI`（`Proc_Seg`）は `"ASSOCIAT"`、`SEGFOPEN` は `"FILEOPS "`、
`USERPROG` は `"KERNEL  "` と読め、いずれも同じファイル内に存在するセグメントに対応する。

## 3. code segment ヘッダ（11 ワード）

3.1 ヘッダはセグメントの最下位アドレスにある：**[マニュアル p.8]**

| word | バイト | 欄 |
|---|---|---|
| 0 | `0x00` | routine dictionary ポインタ（セグメント内ワード・オフセット） |
| 1 | `0x02` | relocation list ポインタ |
| 2–5 | `0x04` | セグメント名、8 文字 |
| 6 | `0x0c` | byte sex 指示子 |
| 7 | `0x0e` | 定数プール・ポインタ（セグメント内ワード・オフセット）、0 なら定数プール無し |
| 8 | `0x10` | `REALSIZE`：2 または 4 ワード |
| 9–10 | `0x12` | 予約 |

3.2 3 つのポインタはいずれも**セグメント内相対**である。Codepool がセグメントごと
運んでしまうからだ。**[マニュアル p.9]**

3.3 **[PME]** 8086 インタプリタがセグメント切り替え時に読むのは、まさにこの 3 枠である——
セグメント内 `+0x00` を 2 倍して `ss:36h`（手続き辞書基底）、`+0x0c` を `ss:44h`（byte sex）、
`+0x0e` を 2 倍して `ss:42h`（定数プール基底）。
**マニュアルと実装が独立した 3 つのオフセットで互いを裏づけている。**
証拠は `docs/10-interpreter/segment-switching.ja.md` のヘルパ `0x0fba`。

3.4 **[標本]** 28 セグメントのヘッダはすべて解析に成功する。名前は読め、`REALSIZE` は
一律 4（`$R4`、すなわち 64 ビット実数に対応し、`LDCRL` がスタックに 8 バイト空けるのと整合）。

3.5 **[標本]** 28 セグメントの routine dictionary ポインタは**常に `Code_Leng − 1` に等しい**。
これは観測された不変量でマニュアルの記述ではない。実装はこれに依存しては**ならない**が、
健全性検査には使える。

> **予約の 2 ワードはゼロではない。** 標本ではセグメントごとに変化し（例えば `KERNEL` は
> `(4184, 38466)`、`GOTOXY` は `(4199, 5733)`）、同じコンパイル単位のセグメントは
> しばしば同じ値を持つ。用途は不明で、未解決項目として挙げておく。

## 4. byte sex

4.1 ヘッダの byte sex 指示子は、そのセグメントを生成した機械の上では**常に 1**。
逆のバイト順で読むと 256 になる。**[マニュアル p.10]**

4.2 影響を受けるワード指向の情報は 2 種に分かれる。**superstructure**（例：routine
dictionary）はロード時に OS が反転する。**embedded**（`LDC` が取る定数、`XJP` の case 表）は
実行時にインタプリタが反転する。**[マニュアル p.10]**

4.3 **[PME]** インタプリタ側の半分は確かに存在する。`ss:44h` が 1 でないとき、
`MOV`、`LDC`、`XJP` はワード単位でバイトを交換する経路を通る。

4.4 **[標本]** `SYSTEM.PASCAL` の 28 セグメントのうち **6 つ**（`STRINGOP`、`HEAPOPS`、
`LOCK`、`COMMANDI`、`PERMHEAP`、`SMALLCOM`）は指示子が 256 と読める。
**1 つの codefile に 2 種類のバイト順が混在しており、しかもそれが OS 自身である。**
ゆえにリーダは初日から byte sex を扱う必要があり、あとから足す例外として扱えない。

4.5 **[再実装]** この実装は**セグメントをその場で反転しない**。ヘッダと routine dictionary は
解析時に byte sex に従って Go の値へ復号し、定数プールとコードはそのまま保ち、
byte sex フラグをセグメントとともに保存して、4.2 の分担に従って実行時に処理させる。

オリジナルはメモリへロードした側をその場で書き換える。倣わない理由は、再実装に
「その場」という概念が無いこと、そして元のバイトを保つことが突き合わせを可能にすること。
**これは表現の選択であり、観測可能な挙動は何も変えない。**

## 5. routine dictionary

5.1 セグメントの最初のワードが routine dictionary を指す。辞書はルーチンのコードを指す
ポインタの並びで、各々セグメント内ワード・オフセット。辞書のワード 0 はセグメント内の
ルーチン数。ルーチン番号は 1..255 で、番号がそのまま添字になる。**[マニュアル p.10]**

5.2 **辞書はアドレスの低い方向へ伸びる**。ルーチン n のポインタはセグメント内ワード
`dict − n` にある。

- **[PME]** 呼び出しヘルパ `0x101b` が計算するのは `word_36 − 2×手続き番号` であり、
  `word_36` は `2 × ヘッダのワード 0`。
- **[標本]** 28 セグメントをこの方向で解析すると、465 個の辞書項目のどれ一つ境界を
  越えない。逆方向ではただちにセグメント末尾を越える。

5.3 `EXTERNAL` と `FORWARD` のルーチンの辞書項目は 0。**[マニュアル p.10]**
**[標本]** 28 セグメントに空項目が 35 個あり、うち 26 個は `KERNEL` 一つに集まっている。
**[PME]** インタプリタは辞書項目 0 に対して実行時エラーへ跳ぶ（`0x101b` の `test di, di`）。

5.4 ルーチンのセグメント内版面は `EXITIC`、`DATASIZE`、最初の命令が隣り合う形で、
**辞書項目が指すのは真ん中の `DATASIZE`** である：

| セグメント内 word | 内容 |
|---|---|
| `ptr − 1` | `EXITIC`：このルーチンを離れるときに実行するコード。セグメント内バイト・オフセット |
| `ptr` | `DATASIZE`：局所データのワード数。引数を含まない |
| `ptr + 1` | 最初の実行可能命令 |

- **[マニュアル p.11]** はルーチンのコードが「2 つのワード——`DATASIZE` と `EXITIC`——で
  始まる」と述べ、同じ段落で「最初の実行可能命令は `DATASIZE` の直後に続く」とも言う。
  前者は `DATASIZE` が先に読めるが、後者は `EXITIC` が先でなければ成り立たない——
  **マニュアル自身が順序を確定させていない。**
- **[PME]** 呼び出しヘルパ `0x103a` は確定させている。`shl di, 1` が辞書項目をバイト・
  オフセットに変えたあと `mov cx, es:[di]` が取るのは `DATASIZE` で、そのあとの
  `inc di; inc di` でようやく実行すべきコードを指す。次の `or cx, cx; js` が
  ネイティブ・コードの符号判定である。
- **[標本]** コードを持つ 430 本について、`w(ptr)` を `DATASIZE` として読むと中央値 3、
  p90 が 76、最大 5121 で、負のものは 1 本も無い。`w(ptr−1)` を `EXITIC` として読むと
  **境界を越えるものが 1 本も無く、418 本がバイト `0x96`、すなわち `RPU` を直接指す**。
  マニュアルの字面どおりの順序（`EXITIC` が `ptr+1`）にすると
  **299 本が境界を越え、`RPU` を指すものは 0 本**になる。

5.5 `DATASIZE` が負なら最初の命令はネイティブ・コードで、値は 1 の補数。このとき
`EXITIC` は未定義であり、読んではならない。**[マニュアル p.11]**
**[標本]** `SYSTEM.PASCAL` の 430 本に負のものは無く、辞書が 28 セグメントすべてを
`M_Psuedo` と記していることと整合する。

## 6. この spec が実装を許すもの

リーダができること——codefile の全セグメントの列挙、各セグメントの名前／番号／型／機械型／
byte sex／定数プール位置／`REALSIZE`、および各ルーチンのコード開始位置と
`DATASIZE`／`EXITIC`。

**許さないもの**——定数プールの内容、relocation list、segment reference list の解釈、
および一切の実行意味論。それぞれ独自の spec が要る。

## 7. 同状態での検証

`CONFORMED` の敷居は「テストした」ではなく、**オリジナルと同じ状態で突き合わせた**ことである。
手順は、1984 年 DOS 版 p-System を走らせ（`oracle/` 参照）、それが `SYSTEM.PASCAL` の
p-code を実行するあいだ一条ずつ記録し、リーダが解いたものと突き合わせる。
テストは `oracle/conform_test.go`。

**検証できたこと：**

- オリジナルが走らせている code segment のヘッダ 4–11 バイト目は `"USERPROG"` と読める——
  同じファイルからリーダが解いたセグメント名の中にそれがある（3.1 のヘッダ版面）。
- そのセグメントのメモリ上の内容は、ファイル中の `Code_Leng` ワードと **99% 以上一致**する
  （2.3 の長さ定義、3.2 のセグメント内相対オフセット）。
- **400 条の p-code の各 IPC について、メモリ上のバイトとファイル中の同じオフセットの
  バイトが一つずつ一致する。** これは「リーダが算出したセグメント内オフセット」と
  「オリジナルが命令をフェッチするアドレス」を結びつける——1 ワードずれれば全面的に食い違う。
- どの IPC もヘッダより後ろ、routine dictionary より前に落ちる（3.1、5.1）。

**検証できていないこと**（同じく書き出す。未検証 ≠ 誤り）：

- `Seg_Misc` の bit 8／bit 9 の意味（2.5 で未検証と明記済み。標本に変異が無い）。
- `Seg_Famly` の変種レコード（2.7 には静的な自己整合の裏づけしか無い）。
- byte sex が逆のセグメントについて、OS が routine dictionary を反転する詳細（4.2）——
  トレースが触れているのは `USERPROG` 1 セグメントだけで、それはホストと同順である。
- `DATASIZE`／`EXITIC`（5.4）はインタプリタのコードと 430 本の統計から確定したもので、
  実行中に呼び出し列を捕まえて計測したものではない。

## 8. この巡回が残した問題

- ヘッダのワード 9、10（マニュアルは「予約」とする）は標本でゼロではなく、
  セグメントごとに変化する。最初のルーチンの `EXITIC` はたいていワード 11、
  `DATASIZE` はワード 12 に落ちるので、この 2 ワードは確かにどのルーチンにも属さない。用途不明。
- 430 本のうち 12 本は `EXITIC` が `RPU` を直接指さない（`0x30`、`0x84`、`0x60` などを指す）。
  退場列が 1 命令では済まないという読みが妥当だが、1 本ずつ読んではいない。
