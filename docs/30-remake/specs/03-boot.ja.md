# spec 03：自己起動

[English](03-boot.en.md) ｜ **日本語** ｜ [繁體中文](03-boot.md)

状態：**`CONFORMED`**（[spec ゲート](../spec-workflow.ja.md)参照）——
**コマンドラインまで起動し、操作もできる。** `.VOL` を 1 枚与えれば p-System が自力で
立ち上がり、226,623 条の p-code がオリジナルと一条ずつ一致する——起動全体、
オリジナル自身がキー待ちで止まるその瞬間までである。

```
Startup Utility - [1R1.0]
PSYSTEM:SYSTEM.MISCINFO ---> RAMDISK:SYSTEM.MISCINFO
PSYSTEM:SYSTEM.PASCAL   ---> RAMDISK:SYSTEM.PASCAL
...
Root is RAMDISK
Prefix is RAMDISK
SYSTEM.PASCAL is on RAMDISK
Command: E(dit, R(un, F(ile, C(omp, L(ink, X(ecute, A(ssem,? [IV.2.1 R3.3]
```

`F` で Filer に入り、`L` で一覧を出すと、OS が起動時に自分でコピーした 5 つの
ファイルが並ぶ：

```
Filer: L(dir, R(em, C(hng, T(rans, D(ate, Q(uit, B(ad-blks, E(xt-dir,? [6R4.0]
Dir listing of what vol ? RAMDISK:

RAMDISK:
SYSTEM.MISCINFO    2  2-Sep-90           SYSTEM.PASCAL    136 14-Jan-85
SYSTEM.EDITOR    106  9-Dec-85           SYSTEM.FILER      45 20-Dec-84
SYSTEM.LIBRARY   102 27-Dec-84
5/5 files<listed/in-dir>, 397 blocks used, 353 unused, 353 in largest
```

この日付はついでにリーダを検証する。`2-Sep-90`、`14-Jan-85`、`20-Dec-84` は
ディスク上の `daccess` 欄（`B429`、`AAE1`、`A94C`）と一つずつ対応する——
**こちらが解いたディレクトリ形式は、p-System 自身の Filer が表示するものと完全に一致する。**

この文書が扱うのは「オリジナルにも DOS にも頼らず、`.VOL` 1 枚から p-System を
立ち上げるには何が要るか」である。p-machine 本体は [spec 02](02-pmachine-core.ja.md)。
ここではホスト側だけを扱う。

## 1. なぜこの文書が要るのか

突き合わせは既に起動全体を walk できているが、その機械は**オリジナルの横に括りつけられて**
いた——セグメント 1 のネイティブ手続き、ディスク、タスク切り替えはすべてオリジナルに
代行させていた。独立に走らせるには、ホスト側を自分で作る必要がある。

境界は明確で、しかもオリジナル自身が引いている：

| ホストが用意すべきもの | どこから見えるか |
|---|---|
| 起動の瞬間のメモリ版面 | 最初の p-code の前に bootstrap が並べたもの |
| セグメント 1 の埋め込みネイティブ手続き 33 本 | インタプリタ @0x1F56 の 48 枠表の非ゼロ枠 |
| セグメントが未ロードのときの扱い | セグメント切り替えヘルパ @0x0FDF のゼロ検査 |
| タスク切り替え | `SIGNAL`／`WAIT` が実際に並ぶとき |

**それ以外はすべて p-code である。** OS 自身が p-code で書かれている。

## 2. 起動の瞬間

オリジナルは最初の p-code に到達するまでに 8086 命令を 7,218 条消費し、すべて bootstrap
である。その瞬間の状態を測るとこうなる（データ・セグメント paragraph `04D1`）：

```
1251:1AB8 90 CPL   sp=D7C2 mp=D7C2 E_Rec=D7D2 MSPROC=1
```

最初の 1 条は `CPL`——OS の外枠プログラムが自身の最初の手続きを呼ぶところだ。

### ロードされるのはどのセグメントか

`SYSTEM.PASCAL` の中で**いちばん前**にあるもの——`USERPROG`、ブロック 1、3,831 ワード、
41 本のルーチン、セグメント番号 22、外枠は `KERNEL`。
リンカが辞書の直後の 1 ブロックに置いているので、bootstrap は辞書を引かずに読める。

### コードから下へ並べる

```
D800  コード（USERPROG、3831 ワード）
D7DC  SIB           36 バイト
D7D2  E_Rec         10 バイト（6 使用、4 は詰め物）
D7CC  E_Vec          6 バイト
D7C2  最初の MSCW   10 バイト  ← MP も SP もここを指す
      ↓ スタックは下へ伸びる
0178  大域データ
0170  BASE：最外枠
0154  TIB
00E6  SYSCOM
0024  インタプリタの状態領域
```

SIB の `Seg_Base` は `{0000, D800}`——ポインタ 0 は「このデータ・セグメント内にある」の意で、
第 2 ワードがセグメント内オフセット。`E_Vec` は 3 枠しかなく、第 2 枠がその `E_Rec` を指す。

最初の MSCW の `MSSTAT` と `MSDYN` はどちらも大域枠自身を指す——**その外側には誰もいない。**

### データ・セグメント最上部の 3 ブロック

`0xFFFE` から下へ切っていく。3 つとも bootstrap が先に読み込んだものだ：

```
FFFE  ← スタック上限（TIB +6 が記録している値）
F7FE  ディスク・ディレクトリ、4 ブロック
F5FE  OS codefile のセグメント辞書、1 ブロック
      ↑ 別セグメントをロードするとき (Code_Addr, Code_Leng) をここで引く
```

ディレクトリの写しは**ディスク上のものの複製ではない**。bootstrap は第 0 件の `+14h` を
**今回の起動日**（UCSD のパック形式：月 4 ビット、日 5 ビット、年 7 ビット）に置き換え、
ディスク側はそのまま残す。`psystem.Options.Date` がその値である。

セグメント辞書のブロックはそのまま運ばれた 512 バイトで、中身は
`(Code_Addr, Code_Leng)` の対が辞書と同じ順に並んでいるだけだ。

### ディレクトリは 2 部ある

1 部はデータ・セグメント最上部（`0xF7FE`）で `SYSCOM+8` が指す。もう 1 部は `0x3AF0` で、
OS 自身が使う。**どちらにも起動日を押す必要がある。**
2 部目の位置は実測で、どう算出されるかは未解である。

## 3. まだ解けていないもの：bootstrap 自身

**bootstrap がデータ・セグメントの低位に残す初期値**（`internal/psystem/machine.go` の
`bootWords`）は、出所の異なる 3 ブロックに分かれる：

### あの一塊はインタプリタ自身の初期化データ

**`SYSTEM.PME.86` の先頭 512 バイトは、そのままデータ・セグメントの同じオフセットへ運ばれる**——
非ゼロの 37 ワードを一つずつ照合して、1 つも違わなかった
（`TestInterpreterDataComesFromItsOwnHeader`）。

その区間がコード・セグメントで見えないのは、ローダが `0x1D56` からのディスパッチ表を
イメージ・オフセット 0 へ移して上書きするからだ。**データ・セグメントの中でだけ生きている**——
そしてそれが、あの 512 バイトがファイル上では意味不明な定数の山に見える理由でもある。

中身はインタプリタによる OS への自己紹介である：

| 位置 | 何か |
|---|---|
| `0x08` | SYSCOM のアドレス（`0x00E6`） |
| `0x0A`／`0x0C`／`0x0E` | 状態領域における局所基底・大域基底・現在の E_Rec のオフセット（`0x26`／`0x28`／`0x3E`） |
| `0x12`–`0x18` | 4 つのネイティブ・コールバックの入口 |
| `0x1A`–`0x22` | その他のインタプリタ・コードのアドレス |

前 4 項に相当するものはこちらにもある——**あのオフセットこそ `internal/psystem` の定数だ。**
`0x12` 以降は 8086 機械語のアドレスで、Go のホストに対応物は無い。OS が必要とするのは
`NAT` 呼び出しのときだけで、`NAT` はそもそも実行できない。そのまま写しているのは、
そこを読む p-code に同じ道を通らせるためである。

同じ一塊には SYSCOM（デバイス数とパラメータ）、byte sex の初期値、最外枠の
`MSSTAT`／`MSDYN`、SYSCOM を指す大域変数 1 も入っている——すべてファイル内にある。

### bootstrap 自身が算出するのは数枠だけ

| 位置 | 何か |
|---|---|
| `0x06` | 起動パラメータ領域のアドレス |
| `0x150` | データ・セグメントの物理アドレス |
| `0x14E`／`0x152` | 未解 |
| TIB `+4`／`+6` | このタスクのスタック上下限（`04A6`／`FFFE`）。算出方法は未解 |

**未解なのはこの 4 枠だけ。** 残りはすべて出典がある。

しかもそれだけではない。「起動の瞬間のデータ・セグメント」を丸ごと比較すると
（`TestSelfBootInitialStateDiff`）、最初は **1,982 区間**が食い違っていた。

最大の一塊は突き止めた——**`SYSTEM.CONFIG`** である。ディスク上のブロック 38–67、
14,848 バイトを bootstrap が丸ごと `0x5020` へ読み込み、先頭 5 ブロックをもう 1 部
`0x06F0` に置く。中身はこの機械のデバイス構成——ドライバ名（`DOSVV.`、`SERPAR`、`BRIDGE`）と、
unit ごとに 1 件 40 バイトのレコード（版面は §4）。OS はこれをもとに `ss:112h` が指す
ユニット表を組む。これを補うと差は 1,982 区間から **540 区間**に落ち、
残りの塊（2 部目・3 部目のディレクトリ写し、構成の作業用複製）も正しく置くと **409 区間**になる。

見つけ方は、ディスク上の各ファイルの先頭 32 バイトをメモリ中から探す
（`cmd/bootdump -findfile`）。**bootstrap を逆アセンブルするより速く、
しかも答えは実際に起きたことである。**

### この数字はゼロにならない

残る 409 区間のうち **397 区間は 8086 機械語**である。`0x0192`–`0x06EF` は bootstrap が
インタプリタ・イメージ `0x3AA2` から運び込んだネイティブ・ドライバ、
`0x42F0`–`0x5010` は PSP と `PSYSTEM.COM` そのもの。OS は前者を `NAT` で呼ぶ。
**こちらのホストは Go なので、その 2 塊はもともと存在しない**——やるべきは
その機能を Go で実装して `NAT` 呼び出しを捕まえることであって、バイトを写すことではない。

したがってこの指標は 2 つに分けて読む必要がある——`409 区間（うち 397 区間はホストの機械語）`。

直感に反する事実がある。**この 1,982 区間を欠いたままでも、最初の 40,619 条の p-code は
一条ずつ一致する。** OS がそれらを読みに行くのはずっと後だからだ。ゆえに「動く」は
「正しく組めた」と同義ではなく、2 つの指標は分けて見なければならない。

## 4. セグメント 1 のネイティブ手続き

@0x1F56 から 48 枠、非ゼロ 33 枠、相異なるもの 26 本。起動中に使われるのは 17 本。

実装済み：

| 手続き | アドレス | 内容 |
|---:|---|---|
| 4 | `0x1B2A` | ロード直後のセグメントのアドレスを relocation list に従って修正 |
| 14 | `0x1AE4` | 2 つの codepool 位置のあいだでセグメント全体を移動 |
| 15／16 | `0x191E`／`0x1970` | `MOVELEFT`／`MOVERIGHT` |
| 18／19 | `0x2C5A`／`0x2C5F` | `UNITREAD`／`UNITWRITE` |
| 21 | `0x18DD` | `FILLCHAR` |
| 23／30 | `0x2B0D`／`0x2B02` | `IOCHECK`／`IORESULT` |
| 24／25 | `0x1A6E`／`0x1A94` | codepool ↔ データ・セグメントのバイト転送 |
| 26 | `0x1ABA` | ロード直後のセグメントをワード単位でバイト交換 |
| 27／28 | `0x19F4`／`0x1A00` | 割り込み禁止／許可 |
| 39／46 | `0x1BAF` | セグメントをディスクから codepool へ読み込む |
| 20 | `0x2CB8` | `TIME(var hi, lo)`：システム時計、1／60 秒単位 |
| 22 | `0x1992` | `SCAN`：mode 0 なら等しいものを、非 0 なら等しくないものを探す。個数は符号付き |
| 29 | `0x1841` | `ATTACH`：セマフォを `ss:4Eh` の割り込みベクタ表に繋ぐ |
| 34／44 | `0x2C36` | デバイスの完了待ち（モード 4） |
| 36／45 | `0x2C1B` | デバイス状態の問い合わせ（モード 8） |
| 38 | `0x1CF6` | 8 バイトの名前で二分木を引く（`+8` と `+0Ah` が左右） |

未実装：`31`／`33`（モード 3）、`47`（別の浮動小数点ルーチン群への差し替え。
**@0x1F56 の表そのものを書き換える**）、およびコードを読んでいない数本。
起動全体にこれらは不要である。

デバイス族は実は 1 本で、`0x2AA0` のモード・バイトで分かれる——1 読み、2 書き、3、
4 待ち、8 状態。引数ブロックはインタプリタ・イメージの `0x2AA0`–`0x2AA8`。

引数の順序は常にそのルーチンの `pop` の順から読み取る。例えば `MOVELEFT` は先に個数を
pop し、次に転送先の（基底, オフセット）対、最後に転送元——`movs` の `es:di ← ds:si` と合う。

### キーが無いときに無理に答えない

実機ではコンソールの読み取りは**ブロックする**。一条ずつ進む方式ではブロックできないので、
読めるキーが無ければこの 1 条まで戻し、`NeedInput` を返す。利用側が `Machine.Keys` を
補って `Run` すれば同じ 1 条から再開する。

「0 バイト読んだ、IORESULT 0」と適当に答えるとどうなるか——**OS はバッファに残った
古い文字を新しい打鍵とみなし**、同じ命令が延々と繰り返される（実測では Filer の
memlock／swappable が交互に点滅し続ける）。この種の誤りはエラーにならず、
ただ機械が狂ったように見えるだけだ。

### デバイス表は `SYSTEM.CONFIG` から解いた

あの 14,848 バイトはもはや丸写しではない。版面は **1 件 40 バイト**：

	+0  同じ類の中で何番目か
	+1  類別（1 コンソール、2 シリアル／パラレル、3 ディスク、4／5 その他）
	+3  0 ならこの件がドライバをロードする。非 0 なら前件と共用
	+4  ドライバ・ファイル名の長さ、続いて最大 11 文字

ディスク類を解くとこうなる：

| unit | 何番目 | ドライバ |
|---:|---:|---|
| 4／5 | 0／1 | `FLOPPY.DRV` |
| 9–12 | 2–5 | `FDISK.DRV` |
| **13** | 6 | **`RAMDSK.DRV`** |
| **14** | 7 | **`DOSVV.DRV`** |
| 15–19 | 8–12 | `DOSVV.DRV`（ドライバ共用） |

ディスク類の unit 番号の並びはマニュアルが定めている（4、5 が最初の 2 台、
9–12 が 3 台目から 6 台目、以降は順に上へ）。**この並びは実測と一致する**——
オリジナルが「在る」と答える unit はまさに 13 と 14 である。ゆえに RAM ディスクが
どこに付き、起動ディスクがどれかは、いまや調べた結果であって、直書きの 2 数字ではない。

他の類の unit 番号規則は未検証なので、それらの件の番号は空けてある——
推測の番号を書き込むと、あとでどれが実測か区別できなくなるからだ。

### ディスクが無いのはエラーではない

OS は起動時に unit を順に問う。**ディスクが無いときは 9（そのボリュームが無い）を
返すべきで、2（unit 番号が誤り）ではなく、まして 0 でもない。** 0 を返すと
「そこに何かある」と思い込み、数千命令あとに全く別の顔をして失敗する。

`IORESULT` は TIB にも保存される。`+12h` の上位バイトはその時点の `ss:0E6h` の値である
（@0x160F の `mov ch, ss:0E6h`）。タスク状態の保存ではメモリ上のその 1 部を読む必要があり、
古い値を取るとデバイスの結果を食ってしまう。

### `UNITREAD`／`UNITWRITE`

2 本の機械語はモード・バイトが違うだけで（@0x2C5A の `mov al,1`／@0x2C5F の `mov al,2`）、
引数処理は完全に共用される。スタックを上から下へ辿ると mode、block、length、
バッファの（基底, オフセット）、unit——すなわち Pascal の
`UNITREAD(unit, buf, length, block, mode)` を左から右へ積んだ形だ。
結果は `ss:0E6h`（`IORESULT`。@0x2B3B の第 1 命令で 0 に消される）へ書かれる。

起動中の実測：unit 1 はコンソール（`<ESC>H`、`<ESC>E` といったカーソル制御はここから出る）、
**unit 14 が起動ディスク**——これはこの DOS ホストでの割り当てであって、
マニュアルの規定ではない。

`ss:0E6h` は同時に `MSPROC` の上位バイトでもある（@0x1636 のタスク切り替えで書かれる）。
**1 バイトに 2 つの用途**があるので、インタプリタの状態がそこへ書き戻されるのは
タスク切り替えのときだけだ。呼び出しのたびに書けば `IORESULT` を潰す。

### コンソールは端末であり、制御コードは `SYSTEM.MISCINFO` から来る

unit 1 が受け取るのは素のテキストではなく、エスケープ列の混じったバイト列である。
**その列は直書きではない**——OS は起動時に `SYSTEM.MISCINFO` を読み、`0x3E` から
`(長さ, バイト…)` の形の制御コード定義が並び、`0x4A`／`0x4C` が画面の高さと幅を与える。
このディスクを解くとこうなる：

| 用途 | 列 |
|---|---|
| 前置コード | `1B` |
| カーソル・ホーム | `1B H` |
| 画面末尾まで消去／行末まで消去 | `1B J`／`1B K` |
| カーソル右／左／上／下 | `1B C`／`08`／`1B A`／`1B B` |
| 画面全消去／1 行消去 | `1B E`／`1B L` |
| 絶対位置指定 | `1B Y` のあと `行+32`、`桁+32` |

画面は 25 行 × 80 桁。**`CR` は `LF` を含意する**——復帰だけで改行しないと、
Filer のディレクトリ一覧が同じ行に重なってしまう。

ホスト側はまさにこの表どおりに文字マトリクスを回す——`internal/psystem/screen.go`。
認識できない列は `Unknown` に記録し、推測もせず握り潰しもしない——
推測を誤ったときの症状は画面が「だいたい合っている」ように見えることであり、
それは完全に壊れているより追いにくい。

### 終わったあとどこへ戻るか

`SCXG` は @0x0545 の入口で `si` を `ss:24h` に退避するが、その時点で si が指しているのは
**手続き番号**である。@0x1410 の `inc si` はそのあと、ネイティブ・コードへ跳ぶ直前に来る。
多くのネイティブ手続きは自分でもう一度退避するので（`MOVELEFT` は @0x192C）、
手続き番号の次に復帰する。

**自分で退避しない数本は違う。** 手続き 4 がそれだ。出口は @0x0200（`ss:24h` から si を
復元する）なので、手続き番号のバイトに戻り、そのバイトが次の命令として実行される——
`04` は `SLDC 4` である。これは丸めてよい些事ではなく、1 バイトずれれば以降すべてが狂う。

## 5. 受け入れ

指標は 2 つ、分けて見る：

| テスト | 何を釘付けにするか | 現在 |
|---|---|---|
| `TestBootReachesTheCommandLine` | **起動するか**（オリジナル不要） | コマンドラインまで到達し、キー待ちで停止 |
| `TestFilerListsTheRAMDisk` | **操作できるか**（オリジナル不要） | `F`→`L`→5 ファイルを一覧 |
| `TestSelfBootMatchesTheOriginal` | 走らせた p-code が同じか | 226,623 条、起動全体 |
| `TestSelfBootInitialStateDiff` | 起動時の状態を正しく組めたか | 残り 409 区間、うち 397 区間はホストの機械語 |

前者は下限（上げることしか許さない）、後者は上限（下げることしか許さない）。

`TestSelfBootMatchesTheOriginal`——自力で起動し、オリジナルと一条ずつ IPC、SP、TOS、
E_Rec を比べる。

**下限が釘付けにしているのは「起動状態を誤って組んではいけない」ことである。**
walk し切れないのはこのテストの失敗ではない——ホスト側にまだ作っていないものがある、
という意味だ。現在の下限は 226,000、実際の walk は 226,623、
すなわちオリジナル自身がキー待ちで止まるその瞬間までである。

## 6. スケジューラ

`SIGNAL`／`WAIT` のブロック経路は p-machine 自身の仕事であってホストのものではない。
触るのはデータ・セグメント内の 3 本のリストだけだ。

| 位置 | 何か |
|---|---|
| `ss:38h` | ready queue の先頭。**走っているタスクも入ったままで、しかも先頭にいる** |
| `ss:3Ch` | 現在のタスク |
| セマフォ `+2` | そのセマフォを待つ TIB のリスト |

`WAIT` に残高が無いとき——自分を ready queue から外し（@0x1722）、優先度順にセマフォの
待ち行列へ挿入し（@0x16E9）、`TIB+14h` に待っているセマフォを記録して切り替える。
`SIGNAL` に待ち手がいるとき——行列の先頭を起こし、その `+14h` を消し、ready queue へ入れ、
**起こした側の優先度が自分より低くない場合にだけ切り替える**（@0x17C7 の `jb`）。
優先度は `TIB+2` の**下位バイト**で、上位バイトはフラグ。

切り替えそのもの（@0x17E8）——状態を現在の TIB へ保存し、activity を 1 回数え、
`ss:3Ch` ← `ss:38h`、そして一式を復元する。

> オリジナルは**次の命令境界まで切り替えを遅らせる**。ディスパッチ表を丸ごと同じアドレスで
> 埋め（@0x18A6）、次の 1 条が何であれ切り替えのコードに落ちるようにし、
> 済んだら表を書き戻す（@0x1892）。あの `dec si` は `lodsb` が既に取ったバイトを
> 返すためにある。一条ずつ進むこちらでは、この 1 条の末尾で切り替えれば同じことだ。

`psystem` 側は**oracle のものを一切 import しない**。オリジナルはテストにしか現れない。

## 7. 途中で詰まった箇所

どれも記録に値する。いずれも「推測では当たらないが、測れば見える」種類のものだからだ：

**局所変数は空ではない。** オリジナルは局所データを確保する前にスタック検査ヘルパへ
`call` し（@0x104F）、その `call` が戻り番地を旧 SP の下に積む——そこはちょうど
**いちばん番号の大きい局所変数**になる位置だ。起動途中には `DATASIZE` が 1 の手続きが
実際にそれを引数として渡す。その値を再現しないと 40,619 条目で食い違う。

**`ss:0E6h` は二役を担う。** `IORESULT` であり、`MSPROC` の上位バイトでもある。
タスク状態の保存ではその時点のメモリ上の 1 部を読む必要があり、
構造体内の古い値を取るとデバイスの結果を食ってしまう。

**ディスク未装着・デバイス未対応・そのファイルが無い、は 3 つの異なる答えである**
（9／3／10）。OS は起動時に unit 2 から 22 まで問い、1 つ誤答すると別の道を進む。

**unit 13 は空の RAM ディスクである。** 750 ブロック、名前は `RAMDISK`、
**起動時にはファイルが 1 つも無い**——OS 自身が `SYSTEM.MISCINFO` ほか 5 つのファイルを
起動ディスクからコピーし、ルートをそちらへ切り替える。この 1 枚が無ければ起動の流れは
まるごと変わる。

**unit 128 は DOS ホストのファイルシステムへの門である。** これは DOS 版に特有のもので、
p-System が下の DOS のファイルを直接読み書きできるようにする。
**Go のホストの下に DOS は無いので、この道の答えは常に「無い」**である。これは `NAT` と
同じ種類の境界であり、「まだ作っていない」ではなく「この機械にそれは存在しない」だ。

やりとりの形は実測した——7 バイトの要求ブロック `{命令, バッファ・アドレス, 長さ, フラグ}`
を書くと、ドライバが第 1 ワードを状態コード 3 に置き換える。続いてそのバッファ内の
データ（2 バイト）を書き、IORESULT 10（そのファイルは無い）が返る。
OS は起動時に一度問い、「無い」を得て先へ進む。
