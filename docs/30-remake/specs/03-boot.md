# spec 03：自己開機

狀態：**`DRAFT`**（見 [spec 閘門](../spec-workflow.md)）。
狀態：**開到命令列，而且用得動。** 一片 `.VOL` 進去，p-System 自己開起來，
226,623 條 p-code 與原版逐條相同——那是整段開機，
走到原版自己也停在等鍵盤的那一刻。

```
Startup Utility - [1R1.0]
PSYSTEM:SYSTEM.MISCINFO ---> RAMDISK:SYSTEM.MISCINFO
PSYSTEM:SYSTEM.PASCAL   ---> RAMDISK:SYSTEM.PASCAL
...
Root is RAMDISK
Prefix is RAMDISK
SYSTEM.PASCAL is on RAMDISK
Command: E(dit, R(un, F(ile, C(omp, L(ink, X(ecute, A(ssem,? [IV.2.1 R3.3]
```

按 `F` 進 Filer、按 `L` 列目錄，列出來的是作業系統開機時自己複製過去的五個檔案：

```
Filer: L(dir, R(em, C(hng, T(rans, D(ate, Q(uit, B(ad-blks, E(xt-dir,? [6R4.0]
Dir listing of what vol ? RAMDISK:

RAMDISK:
SYSTEM.MISCINFO    2  2-Sep-90           SYSTEM.PASCAL    136 14-Jan-85
SYSTEM.EDITOR    106  9-Dec-85           SYSTEM.FILER      45 20-Dec-84
SYSTEM.LIBRARY   102 27-Dec-84
5/5 files<listed/in-dir>, 397 blocks used, 353 unused, 353 in largest
```

那幾個日期順帶把讀取器驗了一次：`2-Sep-90`、`14-Jan-85`、`20-Dec-84`
與磁碟上 `daccess` 欄位（`B429`、`AAE1`、`A94C`）逐一對得上——
**我們解出來的目錄格式與 p-System 自己的 Filer 顯示的完全一致。**

這一份講的是「不靠原版、不靠 DOS，怎麼從一片 `.VOL` 把 p-System 跑起來」。
p-machine 本身在 [spec 02](02-pmachine-core.md)；這裡只講宿主。

## 1. 為什麼需要這一份

對拍已經走完整段開機（201,044 條逐條一致），但那台機器是**掛在原版旁邊**的：
段 1 的原生程序、磁碟、換 task 全部交給原版代跑。要獨立跑起來，
宿主這一側缺的東西得自己做出來。

界線很清楚，而且是原版自己畫的：

| 宿主要提供的 | 從哪裡看出來 |
|---|---|
| 開機那一刻的記憶體版面 | bootstrap 在第一條 p-code 之前擺好的東西 |
| 段 1 的 33 支內嵌原生程序 | 直譯器 @0x1F56 那張 48 格表的非零格 |
| 段還沒載入時的處理 | 切段助手 @0x0FDF 的零檢查 |
| 換 task | `SIGNAL`／`WAIT` 真的要排隊時 |

**其餘全部是 p-code。** 作業系統自己就是 p-code 寫的。

## 2. 開機那一刻

原版跑到第一條 p-code 用掉 7,218 條 8086 指令，全部是 bootstrap。
那一刻的狀態量出來是這樣（資料段 paragraph `04D1`）：

```
1251:1AB8 90 CPL   sp=D7C2 mp=D7C2 E_Rec=D7D2 MSPROC=1
```

第一條是 `CPL`——作業系統的外層程式呼叫它自己的第一支程序。

### 載入的是哪一段

`SYSTEM.PASCAL` 裡**排在最前面**的那一段：`USERPROG`，block 1，3831 個 word，
41 支常式，segment number 22，外層是 `KERNEL`。
連結器把它擺在 dictionary 後面第一塊，所以 bootstrap 不必查 dictionary 就讀得到。

### 由程式碼往下擺

```
D800  程式碼（USERPROG，3831 words）
D7DC  SIB          36 byte
D7D2  E_Rec        10 byte（用 6，補 4）
D7CC  E_Vec         6 byte
D7C2  第一個 MSCW  10 byte  ← MP、SP 都指這裡
      ↓ 堆疊往下長
0178  全域資料
0170  BASE：最外層的框
0154  TIB
00E6  SYSCOM
0024  直譯器的狀態區
```

SIB 的 `Seg_Base` 是 `{0000, D800}`——指標為 0 表示「就在資料段裡」，
第二個 word 是段內偏移。E_Vec 只有三格，第 2 格指向那個 E_Rec。

第一個 MSCW 的 `MSSTAT` 與 `MSDYN` 都指向全域框自己：**外面沒有別人了**。

### 資料段最上面三塊

由 `0xFFFE` 往下切，三塊都是 bootstrap 先讀進來的：

```
FFFE  ← 堆疊上界（TIB +6 記的就是它）
F7FE  磁碟目錄，4 塊
F5FE  作業系統 codefile 的 segment dictionary，1 塊
      ↑ 要載別的段時 (Code_Addr, Code_Leng) 從這裡查
```

目錄那一份**不是磁碟上那一份的複本**：bootstrap 會把第 0 筆的 `+14h`
換成**這次開機的日期**（UCSD 打包格式：月 4 位、日 5 位、年 7 位），
磁碟上那一份不動。`psystem.Options.Date` 就是它。

段 dictionary 那一塊是原封不動搬進來的 512 個位元組，
內容就是 `(Code_Addr, Code_Leng)` 一對一對排下去，順序與 dictionary 相同。

### 目錄有兩份

一份在資料段最上面（`0xF7FE`），`SYSCOM+8` 指著它；另一份在 `0x3AF0`，
作業系統自己用。**兩份都要蓋上開機日期。**
第二份的位置是量到的，怎麼算出來的還沒解。

## 3. 還沒解出來的：bootstrap 本身

**bootstrap 在資料段低位址處留下的初值**（`internal/psystem/machine.go` 的
`bootWords`）分三塊，來源不同：

### 那一整塊是直譯器自己的初始資料

`SYSTEM.PME.86` **檔案開頭那 512 個位元組會被原封不動搬進資料段的同一個
偏移**——非零的 37 個 word 逐一對過，一個不差
（`TestInterpreterDataComesFromItsOwnHeader`）。

那一段在程式碼段裡看不到，因為載入器把 `0x1D56` 起的 dispatch 表搬到映像
偏移 0 蓋掉了它。**它只在資料段裡活著**——這也解釋了為什麼那 512 個位元組
在檔案裡看起來像一堆沒有意義的常數。

內容是直譯器對作業系統的自我介紹：

| 位置 | 是什麼 |
|---|---|
| `0x08` | SYSCOM 的位址（`0x00E6`）|
| `0x0A`／`0x0C`／`0x0E` | 區域基底、全域基底、目前 E_Rec 在狀態區的偏移（`0x26`／`0x28`／`0x3E`）|
| `0x12`–`0x18` | 四個原生回呼的進入點 |
| `0x1A`–`0x22` | 其他直譯器碼位址 |

前四項我們自己也有同樣的東西——**那幾個偏移就是 `internal/psystem` 裡的常數**。
`0x12` 之後那些是 8086 機器碼的位址，Go 宿主沒有對應的東西：
作業系統只在 `NAT` 呼叫時用得到，而 `NAT` 本來就做不到。
照抄是為了讓讀到那幾格的 p-code 走同一條路。

同一塊裡還有 SYSCOM（裝置數與參數）、byte sex 的初值、最外層那個框的
`MSSTAT`／`MSDYN`、全域變數 1 指向 SYSCOM——全部都在檔案裡。

### bootstrap 自己算的只有幾格

| 位置 | 是什麼 |
|---|---|
| `0x06` | 開機參數區的位址 |
| `0x150` | 資料段的實體位址 |
| `0x14E`／`0x152` | 還沒解 |
| TIB `+4`／`+6` | 這個 task 的堆疊上下界（`04A6`／`FFFE`），怎麼算的還沒解 |

**剩下沒解出來的就只有這四格。** 其餘全部有出處。

而且不只這些。把「開機那一刻的資料段」整個比一次
（`TestSelfBootInitialStateDiff`），一開始有 **1,982 段**不同。

最大的一塊查出來了：**`SYSTEM.CONFIG`**。磁碟上 blocks 38–67、14,848 個位元組，
bootstrap 把它整份讀進 `0x5020`，前 5 塊另外再放一份在 `0x06F0`。
裡面是這台機器的裝置組態——驅動的名字（`DOSVV.`、`SERPAR`、`BRIDGE`）、
每個 unit 的 24 位元組記錄。作業系統靠它建 `ss:112h` 指的單元表。
補上這一份，差異從 1,982 段掉到 **540 段**。

怎麼找到的：拿磁碟上每個檔案的前 32 個位元組去記憶體裡搜
（`cmd/bootdump -findfile`）。**比反組譯 bootstrap 快，而且答案是實際發生的事。**

### 這個數字歸不了零

剩下的 540 段裡有 **106 段是 8086 機器碼**（`0x0192`–`0x06EF`）。
那是 bootstrap 從直譯器映像 `0x3AA2` 搬進來的原生驅動，作業系統用 `NAT` 呼叫它。
**我們的宿主是 Go，那一塊本來就不會有**——要做的是用 Go 實作它的功能、
攔下那些 `NAT` 呼叫，不是把位元組抄過來。

所以這個指標要分兩半看：`540 段（其中 106 段是原生驅動）`。

一個反直覺的事實：**缺這 1,982 段，前 40,619 條 p-code 還是逐條相同。**
作業系統要走到很後面才會去讀它們。所以「跑得動」不等於「建對了」，
兩個指標要分開看。

## 4. 段 1 的原生程序

@0x1F56 起 48 格，非零 33 格，相異 26 支。開機途中會用到 17 支。

已經做出來的：

| 程序 | 位址 | 做什麼 |
|---:|---|---|
| 4 | `0x1B2A` | 照 relocation list 修剛載入那一段的位址 |
| 14 | `0x1AE4` | 在兩個 codepool 位置之間搬整段 |
| 15／16 | `0x191E`／`0x1970` | `MOVELEFT`／`MOVERIGHT` |
| 18／19 | `0x2C5A`／`0x2C5F` | `UNITREAD`／`UNITWRITE` |
| 21 | `0x18DD` | `FILLCHAR` |
| 23／30 | `0x2B0D`／`0x2B02` | `IOCHECK`／`IORESULT` |
| 24／25 | `0x1A6E`／`0x1A94` | codepool ↔ 資料段搬位元組 |
| 26 | `0x1ABA` | 把剛載入的段逐 word 交換位元組 |
| 27／28 | `0x19F4`／`0x1A00` | 關中斷／開中斷 |
| 39／46 | `0x1BAF` | 把一段從磁碟讀進 codepool |

| 20 | `0x2CB8` | `TIME(var hi, lo)`：系統時鐘，1／60 秒 |
| 22 | `0x1992` | `SCAN`：mode 為 0 找相等、不是 0 找不等；個數帶正負號 |
| 29 | `0x1841` | `ATTACH`：把號誌掛到 `ss:4Eh` 的中斷向量表 |
| 34／44 | `0x2C36` | 等裝置做完（模式碼 4） |
| 36／45 | `0x2C1B` | 問裝置狀態（模式碼 8） |
| 38 | `0x1CF6` | 用 8 個位元組的名字查一棵二元樹（`+8` 與 `+0Ah` 是兩邊） |

還沒做的：`31`／`33`（模式碼 3）、
`47`（換一組浮點常式，**它會改寫 @0x1F56 那張表本身**），以及還沒讀過碼的幾支。
整段開機不需要它們。

裝置那一族其實是同一支，靠 `0x2AA0` 的模式碼分：
1 讀、2 寫、3、4 等、8。參數塊在直譯器映像的 `0x2AA0`–`0x2AA8`。

參數次序一律由那一支的 `pop` 順序讀出來。例如 `MOVELEFT` 先 pop 個數，
再 pop 目的的（基底, 偏移）配對，最後是來源——與 `movs` 的 `es:di ← ds:si` 對得上。

### 鍵盤沒東西就不要硬回

真機器上主控台的讀是**會等**的。我們一條一條走沒辦法等，所以碰到沒鍵可讀
就退回這一條指令、把 `NeedInput` 交回去，使用端補上 `Machine.Keys` 再
`Run` 就從同一條繼續。

隨便回一個「讀到 0 個位元組、IORESULT 0」會怎樣：**作業系統把緩衝區裡的
舊字元當成新按鍵**，於是同一個指令一路重複執行下去（實測會看到 Filer 的
memlock／swappable 交替閃個不停）。這種錯不會報錯，只會讓機器看起來瘋掉。

### 裝置表是從 `SYSTEM.CONFIG` 解出來的

那 14,848 個位元組不再只是照搬。版面是 **40 個位元組一筆**：

	+0  同一類裡的第幾個
	+1  類別（1 主控台、2 序列／並列、3 磁碟、4／5 其他）
	+3  0 表示這一筆要載入驅動，非 0 表示與前一筆共用
	+4  驅動檔名的長度，接著最多 11 個字元

磁碟那一類解出來是這樣：

| unit | 第幾個 | 驅動 |
|---:|---:|---|
| 4／5 | 0／1 | `FLOPPY.DRV` |
| 9–12 | 2–5 | `FDISK.DRV` |
| **13** | 6 | **`RAMDSK.DRV`** |
| **14** | 7 | **`DOSVV.DRV`** |
| 15–19 | 8–12 | `DOSVV.DRV`（共用驅動）|

磁碟類的 unit 編號順序是手冊定的（4、5 是前兩台，9–12 是第三到第六台，
再往後依序往上）。**這個順序對得上實測**：原版回答「這台在」的正是 13 與 14。
所以記憶體磁碟掛在哪、開機磁碟是哪一台，現在是查出來的，不是寫死的兩個數字。

其餘類別的 unit 編號規則還沒查證，那幾筆的編號留空——寫一個猜的號碼進去，
之後查起來會分不出哪個是量到的。

### 沒掛磁碟不是錯誤

作業系統開機時會把 unit 一個一個問過去。**沒掛磁碟要回 9（沒有這片磁碟），
不是 2（錯的 unit 編號），更不是 0。** 回 0 會讓它以為那台有東西，
然後在幾千條指令之後以完全不同的樣子出錯。

`IORESULT` 還會被存進 TIB：`+12h` 的高位元組就是 `ss:0E6h` 當下的值
（@0x160F 的 `mov ch, ss:0E6h`）。存 task 狀態時要讀記憶體裡那一份，
拿舊的會把裝置的結果吃掉。

### `UNITREAD`／`UNITWRITE`

兩支的機器碼只差一個模式碼（@0x2C5A 的 `mov al,1`／@0x2C5F 的 `mov al,2`），
參數處理完全共用。堆疊上由頂往下是 mode、block、length、緩衝區的（基底, 偏移）、unit
——就是 Pascal 的 `UNITREAD(unit, buf, length, block, mode)` 由左往右推。
結果寫進 `ss:0E6h`（`IORESULT`，@0x2B3B 一進去就把它清成 0）。

開機途中量到的：unit 1 是主控台（`<ESC>H`、`<ESC>E` 這些游標控制就是從這裡出去的），
**unit 14 是開機磁碟**——那是這台 DOS 主機的分配，不是手冊規定的。

`ss:0E6h` 同時是 `MSPROC` 的高位元組（@0x1636 換 task 時寫它）。
**同一個位元組兩個用途**，所以直譯器的狀態只有換 task 時才寫回那裡；
每次呼叫都寫會把 `IORESULT` 蓋掉。

### 做完之後回到哪裡

`SCXG` @0x0545 一進來就把 `si` 存進 `ss:24h`，那時 si 指著**程序號**；
@0x1410 的 `inc si` 之後才跳進原生碼。多數原生程序自己會再存一次
（`MOVELEFT` 在 @0x192C），所以還原到的是程序號後面。

**沒有自己存的那幾支不一樣。** 程序 4 就是：它的出口是 @0x0200（會從 `ss:24h`
還原 si），於是回到程序號那個位元組，而那個位元組會被當成下一條指令執行——
`04` 就是 `SLDC 4`。這不是可以四捨五入掉的細節，差一個位元組後面就全錯了。

## 5. 驗收

兩個指標，分開看：

| 測試 | 釘什麼 | 現在 |
|---|---|---|
| `TestBootReachesTheCommandLine` | **有沒有開起來**（不需要原版） | 開到命令列，停在等鍵盤 |
| `TestFilerListsTheRAMDisk` | **用不用得動**（不需要原版） | `F`→`L`→列出五個檔案 |
| `TestSelfBootMatchesTheOriginal` | 跑出來的 p-code 一不一樣 | 226,623 條，整段開機 |
| `TestSelfBootInitialStateDiff` | 開機那一刻的狀態建對了沒 | 還有 409 段，其中 397 段是宿主的機器碼 |

第一個是下限（只准往上），第二個是上限（只准往下）。

`TestSelfBootMatchesTheOriginal`：自己開機，逐條與原版比 IPC、SP、TOS、E_Rec。

**下限釘的是「開機狀態不能建錯」。** 走不完不是這個測試的失敗——
那表示宿主還有沒做出來的東西。目前下限 40,000，實走 40,619。

跑到那裡，主控台上已經是：

```
<ESC>H<ESC>E<ESC>Y8 Copyright 1979 U.C. Regents; Copyright 1985 SofTech Microsystems<ESC>H
```

## 7. 一路上卡住的地方

每一個都值得記，因為每一個都是「照著猜會猜不到、量了就看得見」的那種：

**區域變數不是空的。** 原版在配置區域資料之前會 `call` 進堆疊檢查助手
（@0x104F），那一次 `call` 把返回位址推在舊 SP 底下——而那個位置正是
**編號最大的那個區域變數**。開機途中就有一支 `DATASIZE` 為 1 的程序把它
當參數傳出去。不重現那個值，第 40,619 條就對不上。

**`ss:0E6h` 一格兩用。** 它同時是 `IORESULT` 與 `MSPROC` 的高位元組。
存 task 狀態時要讀記憶體裡當下那一份，拿 struct 裡的舊值會把裝置結果吃掉。

**沒掛磁碟、裝置不支援、沒有這個檔案是三個不同的答案**（9／3／10）。
作業系統開機時把 unit 2 到 22 問一遍，答錯一個它就走上另一條路。

**unit 13 是一片空的記憶體磁碟。** 750 塊、名字 `RAMDISK`、
**開機時一個檔案都沒有**——作業系統自己會把 `SYSTEM.MISCINFO` 等五個檔案
從開機碟複製過去，然後把根目錄切過去。少了這片，開機流程整個不一樣。

**unit 128 是 DOS 主機的檔案系統閘道。** 那是 DOS 版特有的東西——
讓 p-System 直接讀寫底下那台 DOS 的檔案。**Go 宿主底下沒有 DOS，
所以這條路的答案永遠是「沒有」**，這與 `NAT` 是同一種界線：
不是還沒做，是這台機器上不存在那個東西。

往來的形狀量出來了：寫七個位元組的請求塊 `{命令, 緩衝區位址, 長度, 旗標}`，
驅動把第一個 word 換成狀態碼 3；接著寫那個緩衝區裡的資料（兩個位元組），
回 IORESULT 10（沒有這個檔案）。作業系統開機時問一次，得到「沒有」就往下走。

## 6. 排程器

`SIGNAL`／`WAIT` 的阻塞路徑是 p-machine 自己的事，不是宿主的：
它們只碰資料段裡的三條串列。

| 位置 | 是什麼 |
|---|---|
| `ss:38h` | ready queue 的頭。**跑著的那個 task 一直在裡面，而且在最前面** |
| `ss:3Ch` | 目前是哪個 task |
| 號誌 `+2` | 在等這個號誌的 TIB 串列 |

`WAIT` 沒餘額時：把自己從 ready queue 拿掉（@0x1722）、依優先權排進號誌的
等待佇列（@0x16E9）、在 `TIB+14h` 記下在等哪個號誌，然後換人。
`SIGNAL` 有人在等時：把佇列頭叫起來、清它的 `+14h`、放進 ready queue，
**叫起來的那個優先權不低於自己才換人**（@0x17C7 的 `jb`）。
優先權是 `TIB+2` 的**低位元組**，高位元組是旗標。

換人本身（@0x17E8）：存狀態進目前的 TIB、記一次 activity、
`ss:3Ch` ← `ss:38h`，再整份還原。

> 原版是**延到下一條指令的邊界才換**的：它把整張 dispatch 表填成同一個位址
> （@0x18A6），讓下一條無論是什麼都落到換人的碼，換完再把表抄回來（@0x1892）。
> 那個 `dec si` 就是為了把已經被 `lodsb` 取走的位元組還回去。
> 我們一條一條走，在這一條的結尾換就是同一件事。

`psystem` 這一側**不 import 任何 oracle 的東西**：原版只出現在測試裡。
