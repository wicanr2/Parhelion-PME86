# セグメント切り替え：E_Rec、SIB、コード・セグメントのヘッダ

[English](segment-switching.en.md) ｜ **日本語** ｜ [繁體中文](segment-switching.md)

p-machine は一度にひとつの「現在のセグメント」しか持たない。セグメントをまたぐ呼び出しは
コード基底、定数プール基底、大域データ基底を差し替え、さらに 2 つのカウンタを更新して
「どのセグメントを追い出してよいか」を OS に知らせる必要がある。この稿では、8086 版が
それを行う 43 命令を分解する。

> 関連：[インタプリタの状態](machine-state.ja.md)｜[アドレッシング](addressing.ja.md)

## 三段の間接

マニュアル p.37 の `E_Rec` はセグメントの実行時記述子である。この版が実際に使う
フィールド・オフセット：

| オフセット | 内容 | 根拠 |
|---|---|---|
| `+0` | `Env_Data`、セグメントの大域データ基底 | `LAE` ヘルパはこれに 8 を足し、さらに変数オフセットを足す。切り替え時に `word_30` へ書かれ、+8 して `dx` になる |
| `+2` | `E_Vec`、**セグメント番号で引く `E_Rec` ポインタ配列** | `CXL` ヘルパが `bp = segnum×2; bp = [bp + ss:3Ah]` を行い、`ss:3Ah` がまさにこの枠 |
| `+4` | `SIB` | 切り替え時に `word_34` へ書かれ、以後 `+4`／`+6` を数える。意味はマニュアルの `Ref_Count`／`Activity` と合う |

マニュアルの Pascal 宣言は `Env_Data`、`Env_SIB`、`Env_Vect` の順である。
**この実装では第 2・第 3 フィールドがその逆になっている。** `+2` がポインタ配列だという
証拠は独立に 2 つある——セグメント番号×2 で添字され、取り出したものがさらに `E_Rec`
として逆参照される。

## 切り替えのコード

`0x0fab` には 3 つの入口があり、呼び出し側が「どこまで知っているか」に対応する：

```
0fab: d1e5      shl bp, 1            ; 入口 1：bp = セグメント番号
0fad: 032e3a00  add bp, word_3A      ;   E_Vec を引く
0fb1: 8b6e00    mov bp, [bp+0]
0fb4: a13e00    mov ax, word_3E      ; 入口 2：bp = 目標 E_Rec
0fb7: a34000    mov word_40, ax      ;   旧 E_Rec を控える
0fba: 892e3e00  mov word_3E, bp      ; 入口 3：控えない
0fbe: 8b5600    mov dx, [bp+0]       ; Env_Data
0fc1: 89163000  mov word_30, dx      ;   → BASE
0fc5: 83c208    add dx, 8            ;   → 大域データ基底（dx に常駐）
0fc8: 89162800  mov word_28, dx
0fcc: 8b4602    mov ax, [bp+2]
0fcf: a33a00    mov word_3A, ax      ; E_Vec
0fd2: 8b7e04    mov di, [bp+4]
0fd5: 893e3400  mov word_34, di      ; SIB
0fd9: 8b4502    mov ax, [di+2]
0fdc: 3d0000    cmp ax, 0
0fdf: 7439      jz  return           ; ← ZF = セグメントが常駐していない
      ...                            ; コード・セグメントの 8086 セグメント値を算出
0ff7: 8ec0      mov es, ax
0ff9: a32a00    mov word_2A, ax
0ffc: 33ed      xor bp, bp
0ffe: 268b460c  mov ax, es:[bp+0Ch]
1002: a34400    mov word_44, ax      ; byte sex
1005: 268b4600  mov ax, es:[bp+0]
1009: 268b6e0e  mov bp, es:[bp+0Eh]
100d: d1e0      shl ax, 1
100f: a33600    mov word_36, ax      ; 手続き辞書の基底
1012: d1e5      shl bp, 1
1014: 892e4200  mov word_42, bp      ; 定数プール基底
1018: 85ed      test bp, bp
101a: c3        retn
```

`CXL` は入口 1（セグメント番号しか知らない）、`CPF` は入口 2、`RPU` は入口 3 から入る。
**3 つの入口が同じ尾部を共有している**——「セグメント切り替え」を 1 本のルーチンとして
書き、呼び出し側ごとに先頭の数命令を飛ばす作りで、`SLOD1`／`SLOD2` がアドレッシング・
ヘルパを共有するのと同じ手口だ。

戻り値は ZF に乗る。`0x0fdf` の `jz` はそのまま `retn` へ跳ぶので、呼び出し側の `jz` が
「セグメントが常駐していない、segment fault を出せ」を意味する。`CXL` の
`call 0fab; jz 0x143d` がまさにそれである。

## コード・セグメントのヘッダ

上の最後の数命令は、**ロード済みコード・セグメントの先頭**から 3 つの値を読む：

| セグメント内バイト・オフセット | 内容 |
|---|---|
| `0x00` | 手続き辞書のワード・オフセット。インタプリタが 2 倍して `word_36` へ |
| `0x0c` | byte sex フラグ。1 ならホストと同じ |
| `0x0e` | 定数プールのワード・オフセット。2 倍して `word_42` へ |

手続き辞書は**後ろ向きに伸びる**。呼び出しヘルパ `0x101b`：

```
101b: 8f06d600  pop word_D6          ; 呼び出し側の戻り番地
101f: 8f06da00  pop word_DA          ; 呼び出し側が積んだ静的リンク値
1023: 892ed800  mov word_D8, bp      ; bp = 手続き番号
1027: d1e5      shl bp, 1
1029: f7dd      neg bp
102b: 032e3600  add bp, word_36      ; 辞書基底 − 2×手続き番号
102f: 268b7e00  mov di, es:[bp+0]
1033: 85ff      test di, di
1035: 7503      jnz  続行
1037: e9f9f1    jmp  エラー
```

辞書項目が 0 ならエラー。これで `CPL` と `CPG` が 1 行しか違わない理由がわかる：

```
CPL: ff362e00  push word_2E      ; MP   —— 呼び出し側自身の枠を静的リンクに
CPG: ff363000  push word_30      ; BASE —— 大域の枠を静的リンクに
```

残りは完全に同一で、どちらも `call 0x101b` へ続く。

## 2 つのカウンタ

セグメントをまたぐ呼び出しが成功したあと（ヘルパ `0x10db`）：

```
10db: 8b2e2e00  mov bp, word_2E      ; MP
10df: 8b3e4000  mov di, word_40      ; 旧 E_Rec
10e3: 897e06    mov [bp+6], di       ; MSENV ← 旧 E_Rec
10e6: 368b6d04  mov bp, ss:[di+4]    ; 旧セグメントの SIB
10ea: e80800    call 0x10f5          ;   [SIB+6] ← ++カウンタ
10ed: 8b2e3400  mov bp, word_34      ; 新セグメントの SIB
10f1: ff4604    inc word ptr [bp+4]  ;   Ref_Count++
```

`RPU` は逆に `dec word ptr [bp+4]` を行う。`0x10f5` はわずか 5 命令：

```
10f5: 36a11001  mov ax, ss:110h
10f9: 40        inc ax
10fa: 36a31001  mov ss:110h, ax
10fe: 894606    mov [bp+6], ax
1101: c3        retn
```

マニュアルは `Ref_Count` を「未完了のセグメント間呼び出し数」、`Activity` を
「使用回数に応じて累積し、時間とともに増える値」と説明する。`+4` と `+6` の挙動は
それぞれこの記述に対応する。マニュアルの宣言順から計算すると `Ref_Count` は `+2`、
`Activity` は `+4` のはず——**どちらも 2 バイトずれており、これは 8086 版の
`Seg_Base` が 1 ワードではなく 2 ワードを占めることを示す。**

それはこの機械の置かれた状況とも合う。16 ビットのアドレスでは 64 KB の外に届かず、
code pool は 64 KB に収まらない。ヘルパ `0x1bee` はその 2 ワードを 8086 の
セグメント値にたたむ：

```
1bee: 85ed      test bp, bp
1bf0: 7416      jz  → ax = ss
1bf2: 8b4602    mov ax, [bp+2]
1bf5: 8b6e00    mov bp, [bp+0]
1bf8: 51        push cx
1bf9: b104      mov cl, 4
1bfb: d3e8      shr ax, cl           ; 下位ワード >> 4
1bfd: 81e50f00  and bp, 0Fh          ; 上位ワードは 4 ビットだけが有意
1c01: d3cd      ror bp, cl           ;   << 12
1c03: 59        pop cx
1c04: 0bc5      or  ax, bp
1c06: 7502      jnz →
1c08: 8cd0      mov ax, ss           ; 計算結果が 0 ならインタプリタ自身のセグメントに戻す
1c0a: c3        retn
```

つまり 20 ビットのバイト・アドレスを `{上位 4 ビットのワード, 下位 16 ビットのワード}`
として保持し、使うときに 4 ビット右シフトして paragraph にする。ゼロは
「インタプリタ自身のセグメント内にある」を意味する。

## `Seg_Base` はどうやってセグメント値になるのか

`SIB` の先頭 2 ワードは 1 つのアドレスではなく、**ポインタとオフセットの組**である：

| word | 内容 |
|---|---|
| `Seg_Base+0` | Codepool 基底へのポインタ。**インタプリタのデータ・セグメント（`ss`）相対** |
| `Seg_Base+2` | そのセグメントの Codepool 内**バイト・オフセット** |

```
セグメント値 ＝ paragraph(Codepool 基底) ＋ (プール内オフセット ÷ 16)
```

ポインタが 0 なら、そのセグメントはインタプリタ自身のセグメント内にある
（`0x1bee` の `test bp,bp; jz`）。

稼働中のシステムで実測した一組（`ss` ＝ `0x04d1`、`ss:11ac` ＝ `{0001, 4d10}`、
よって Codepool 基底は paragraph `0x14d1`）：

| セグメント | `Seg_Base` | 算出値 | 実際のロード先 |
|---|---|---|---|
| `KERNEL` | `11ac 0020` | `0x14d1 + 0x002` | `0x14d3` |
| `CUPOPS` | `11ac 1420` | `0x14d1 + 0x142` | `0x1613` |
| `GETCMD` | `11ac 2a20` | `0x14d1 + 0x2a2` | `0x1773` |
| `MSGOPS` | `11ac 4620` | `0x14d1 + 0x462` | `0x1933` |
| `COMMANDI` | `11ac b420` | `0x14d1 + 0xb42` | `0x2013` |
| `SMALLCOM` | `11ac ce20` | `0x14d1 + 0xce2` | `0x21b3` |
| `REALOPS` | `11ac d820` | `0x14d1 + 0xd82` | `0x2253` |
| `USERPROG` | `0000 d800` | `ss + 0xd80` | `0x1251` |

8 つすべて的中する。最後の行がポインタ 0 の場合である。

**`0x0fdf` のゼロ検査が見ているのは第 2 ワード**（プール内オフセット）で、
オフセットが 0 ならセグメントは常駐していない——`SCREENOP`、`LOCK`、`FILEOPS` など
その時点で未ロードのセグメントは 2 ワードとも 0 になっている。

`SIB` の残りのフィールドも一致する。`Seg_Name` は `"KERNEL  "`（byte `+12`）、
`Seg_Leng` は 2152（`+20`）と読め、マニュアル p.34 の宣言順どおりだ——
ただし `Seg_Base` を 2 ワードとして数えるかぎりにおいて。

## インタプリタに埋め込まれた手続き

`CXG` は実際に切り替える前にひとつ問う——「これはホストの機械語か？」。
セグメント番号が 1 のとき `0x1F56` から始まる 48 エントリの表を引き、当たれば
セグメントを切り替えずに機械語へ直接跳ぶ。

その表こそ「p-code でないものの完全な一覧」である。項目ごとの内容は
[セグメント 1 に埋め込まれたネイティブ手続き](native-intrinsics.ja.md)を参照。

## 境界

- `Seg_Base` の算出方法は稼働中のシステムでの実測（8 セグメント全的中）であり、
  マニュアルの記述ではない。マニュアルは `Seg_Base` が `Mem_Ptr` だとしか言わない。
- `0x1bee` が読むポインタは `ss` 相対である。コードだけ見ると `es` 相対に見えるが、
  実測はそうではない——**この 1 点は実測を優先する。**
- ネイティブ手続き表の項目ごとの内容は
  [セグメント 1 に埋め込まれたネイティブ手続き](native-intrinsics.ja.md)へ移した。
