# 命令フェッチとディスパッチ：メインループを持たないインタプリタ

[English](dispatch-and-threading.en.md) ｜ **日本語** ｜ [繁體中文](dispatch-and-threading.md)

`SYSTEM.PME.86` は 1984 年 DOS 版 UCSD p-system の p-machine インタプリタで、
サイズは 16,384 バイト。やることは単純だ——1 バイト読み、表を引き、そこへ跳び、
終わったら次の 1 バイトを読む。特異なのは、
**「メインループ」と呼べる場所がどこにも存在しない**ことである。

> 関連：[インタプリタの状態](machine-state.ja.md)｜
> [アドレッシングと活動記録](addressing.ja.md)｜
> [256 エントリ対照表](opcode-map.ja.md)

## ディスパッチ列の姿

すべてのハンドラは同じ 8 バイトで終わる：

```
32e4      xor  ah, ah
ac        lodsb                  ; al ← [ds:si], si++
97        xchg ax, di            ; di ← opcode
d1e7      shl  di, 1             ; ×2 → 表のバイト添字
2eff25    jmp  word ptr cs:[di]  ; ハンドラへ跳ぶ
```

`si` が IPC（instruction pointer counter）であり、`lodsb` 一命令で「読む」と「進める」を
同時に済ませている。169 本のハンドラのうち 129 本が**この列を自分の末尾にそのまま複製**
しており、残りは `jmp` で他のハンドラの末尾に合流するか、エラー経路へ抜ける。

これが direct threading である。**ディスパッチ・コードを各ハンドラへ複製**することで、
「メインループへ戻る」無条件分岐を 1 回節約する。1984 年の 8088 では `jmp` 一回が
およそ 15 クロック、典型的なハンドラはわずか 8 命令だから、節約の比率は小さくない。
代償はハンドラごとに 8 バイト——169 本で 1,352 バイト、インタプリタ全体の 8% にあたる。
**空間を時間に替え、しかも本数分だけ支払う。**

同じバージョンの 68000 インタプリタ（SunDog）は反対側を選んだ。ハンドラの末尾は一律
`jmp (a5)` で、`a5` は唯一のメインループを常時指している。だから「分岐先を数えて
メインループを探す」手口は 68000 版では一発で当たり、8086 版では完全に空振りする——
突出した分岐先がひとつも無いからだ。

## 1 バイト節約する変種

50 本のハンドラは `xor ah, ah` を落として、こう書かれている：

```
97        xchg ax, di
ac        lodsb
97        xchg ax, di
d1e7      shl  di, 1
2eff25    jmp  word ptr cs:[di]
```

最初の `xchg` は `di` を `ax` へ移す。これが等価になるのは
**その時点で `di` の上位バイトがゼロ**である場合だけだ——移ってきたゼロが、
`lodsb` の要求する `ah = 0` の役を果たす。

いちばん綺麗な例が `SLDC 0` である。opcode が 0 のとき、ディスパッチ直後の `di` は
ちょうど 0 になる：

```
0319: 57        push di          ; di = 0×2 = 0、積まれるのは定数 0
      97        xchg ax, di      ; ax ← 0
      ac        lodsb            ; ah は既に 0
      97 d1e7 2eff25
```

`SLDC` は `0x00`–`0x1f` の 32 エントリを占め、「積む定数」を opcode 自身に埋め込んでいる。
`0x00` だけ専用ルーチンを持つのは、そこで `di` がたまたまゼロになるからで、
`0x01`–`0x1f` は `0x0322` を共有する。

## 表はどこにあるか

`jmp word ptr cs:[di]` にはディスプレイスメントが無く、文字どおり「表は `cs:0000` にある」
と言っている——ところがファイル内には表らしきものが見当たらない。そこで既知のものから
逆算する。IV.0 は `BPT`（`0x9e`）を実行時エラーの発生と定義しており、8086 版は
エラー番号を `bp` に入れて共通処理へ跳ぶ：

```
026e: bd1000    mov bp, 16
0271: eb9c      jmp 0x020f
```

値 `0x026e` はファイル全体でただ一度、オフセット `0x1e92` に現れる。これが `0x9e` の
エントリなら、表の先頭は `0x1e92 − 0x9e×2 = 0x1d56`。そこを基点に 256 エントリを読むと
すべてが妥当なコードを指し、各々を逆アセンブルした結果は IV.0 のマニュアルと一致する
（[対照表](opcode-map.ja.md)参照）。

**エントリはファイル・オフセットである**——そして実行時には同時に `cs` 相対アドレスでも
ある。**ローダがその 512 バイトをイメージ先頭へ移す**からだ。

実機で測ると、`SYSTEM.PME.86` は物理 `0x01400`（セグメント `0x0140`）に読み込まれ、
イメージのオフセット `0x000`–`0x1ff` は、ディスク上の `0x1d56` から始まる 512 バイトと
**バイト単位で完全に一致**する。もともとそこにあったアドレス表は上書きされて消える。

その結果、三つのことが同時に成り立つ：

- `cs` はイメージ基底を指すので `cs:0000` が表の先頭になり、
  `jmp word ptr cs:[di]` にディスプレイスメントが要らない。
- エントリはイメージ相対オフセットなので、`cs:offset` として扱えばそのまま
  ハンドラのアドレスになる。
- ファイル先頭側の表はロード中しか意味を持たず、その後は消える
  （[先頭 512 バイト](../20-formats/pme86-header.ja.md)参照）。

この計測は `PSYSTEM.COM` を実行し、マスク表（`0x1fb6` 以降——純粋な定数で再配置されない）
を指紋としてメモリ中のイメージ基底を突き止め、その上でバイト単位に比較している。

## 256 エントリの内訳

| 種別 | エントリ数 | 場所 |
|---|---|---|
| 専用ハンドラ | 163 | — |
| `SLDC` 共有（`0x00` は専用） | 31 | `0x01`–`0x1f` |
| `SLLA` 共有 | 8 | `0x60`–`0x67` |
| `SCXG` 共有 | 8 | `0x70`–`0x77` |
| 未実装（エラー 11） | 44 | `0x40`–`0x5f`, `0xaa`, `0xaf`, `0xf5`–`0xfe` |
| エラー 14 | 1 | `0xff` |
| エラー 16 | 1 | `0x9e`（`BPT`） |

相異なる飛び先は 169。すべて逆アセンブルに成功し、命令数の中央値は 8。80 命令の
打ち切り上限を超えたのは `MPR`（`0x24e1`）と `DVR`（`0x262a`）の 2 本だけである。

## 途中で得られた統計

2,026 命令（打ち切られた部分を除く）を通して：

| レジスタ | 出現数 | | 命令 | 個数 |
|---|---|---|---|---|
| `ax` | 746 | | `mov` | 258 |
| `di` | 571 | | `xchg` | 241 |
| `bp` | 347 | | `lodsb` | 177 |
| `cs` | 135 | | `jmp` | 166 |
| `cx` | 130 | | `shl` | 160 |
| `si` | 129 | | `pop` | 151 |

`xchg` が 2 位に来るのは偶然ではない。8086 の `xchg ax, reg` は 1 バイト、`mov` は
2 バイト。8 命令のハンドラでは、その 1 バイト差が 169 回複製される。`shl` が 5 位なのも
構造的だ——p-code のアドレスはワード単位、8086 のアドレスはバイト単位なので、
**アドレス計算は必ず 2 倍する**ことになる。

## 境界

- 逆アセンブルは「無条件転送に当たったら停止」で打ち切るため、`jmp` の先にあるコードは
  収集されない。`MPR` と `DVR` は 80 命令上限で切れているので、ここの命令統計は
  実際より低めに出ている。
- 「129 本がディスパッチをインライン展開」は末尾 5 命令のバイト列比較によるもので、
  途中で分岐する末尾は扱えていない。
