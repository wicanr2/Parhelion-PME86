# インタプリタの状態：4 本のレジスタと十数個の変数

[English](machine-state.en.md) ｜ **日本語** ｜ [繁體中文](machine-state.md)

p-machine はスタックマシンである。マニュアル p.13 が挙げるレジスタは `SP`、`MP`、
`BASE`、`IPC`、`SEG`、`JTAB`、`NP`。8086 は 16 ビット・レジスタを 8 本しか持たず、
そのうち 2 本はディスパッチ列自身が食う。この稿の問いは、
**どの p-machine レジスタを 8086 レジスタに常駐させる価値があるか、残りはどこに置くか**である。

> 関連：[命令フェッチとディスパッチ](dispatch-and-threading.ja.md)｜
> [アドレッシングと活動記録](addressing.ja.md)｜
> [セグメント切り替え](segment-switching.ja.md)

## 常駐レジスタ

| 8086 | 内容 | 根拠 |
|---|---|---|
| `si` | **IPC**、次の opcode を指す | ディスパッチ列が `lodsb` を使う。ヘルパを呼ぶハンドラは必ず先に `mov ss:24h, si` で退避する |
| `sp` | **SP**、評価スタックの頂点 | `push`／`pop` がそのまま p-code のスタック操作になる |
| `bx` | **局所データ基底**、`MP + 8` に等しい | ヘルパ `0x093e` は `bx − 8` から静的チェーンを辿る。`RPU` は復帰時に `word_26 = 新 MP + 8` を書く |
| `dx` | **大域データ基底**、`Env_Data + 8` に等しい | `LAO` は `add ax, dx` 一発。`dx` を壊すハンドラ（`DVI`、`STP` など）は末尾で `mov dx, ss:28h` を補う |
| `ds` | 現在の**コード・セグメント**基底 | `lodsb` が読むのは p-code。`CSP` は使い終わった `ds` を `ss:2Ah` から復元する |
| `ss` | インタプリタ自身のデータ・セグメント | すべての状態変数は `ss:` で参照される |

`ax`、`cx`、`bp`、`di`、`es` は作業用。`di` の出現数（571）が `ax` に次いで多いのは、
ディスパッチ列が毎周それで表アドレスを計算するからである。

**設計上の取引をいちばんよく示すのが、あの `dx` の復元行だ。** 8086 の `div` と `mul` は
`dx` を強制的に使うので、整数除算や packed フィールド書き込みのハンドラは大域基底を
保てない。答えは「`dx` に置かない」ではなく「壊したらメモリから戻す」だった——
1 バイトの `add ax, dx` は大域変数アクセスのたびに現れ、`mov dx, ss:28h` は
ごく少数のハンドラにしか現れない。

## メモリ上の状態変数

以下のオフセットはすべて `ss:` 相対。「使用者」欄は実際に観測されたものだけで、網羅ではない。

| オフセット | 内容 | 使用者 |
|---|---|---|
| `0x24` | 退避した IPC（`si`） | 32 本。ヘルパ呼び出しやセグメント切り替えを行うものすべて |
| `0x26` | 局所データ基底 = `MP + 8`（`bx` のメモリ複製） | `RPU` |
| `0x28` | 大域データ基底 = `Env_Data + 8`（`dx` の複製） | `DVI`、`MPI`、`MODI`、`IXA`、`IXP`、`STP` |
| `0x2a` | 現在のコード・セグメントの 8086 セグメント値 | `CSP`、文字列比較ヘルパ |
| `0x2e` | **MP**、現在の活動記録 | `CPL`、`CPI`、`CXL`、`CXI`、`RPU`、`LSL` |
| `0x30` | **BASE**、`Env_Data` の元の値 | `CPG` |
| `0x32` | 現在の `MSPROC`（手続き番号） | `RPU` |
| `0x34` | 現在セグメントの SIB | セグメント切り替えヘルパ |
| `0x36` | 手続き辞書の基底（セグメント内オフセット ×2） | 呼び出しヘルパ `0x101b` |
| `0x3a` | **E_Vec**、セグメント番号で引く E_Rec ポインタ配列 | `LAE`、セグメント切り替えヘルパ |
| `0x3c` | スタック／ヒープ境界の記録 | スタック検査ヘルパ `0x02da` |
| `0x3e` | 現在の **E_Rec** | `RPU`、セグメント切り替えヘルパ |
| `0x40` | セグメント切り替え中に退避する「旧 E_Rec」 | `CPL`、`CPG`、`CPI`、`RPU` |
| `0x42` | **定数プール基底**（セグメント内バイト・オフセット） | `LCO`、`LDC`、`LDCRL`、`XJP` |
| `0x44` | **byte sex フラグ** | `LDC`、`MOV`、`XJP` |
| `0x46` | スタック検査が算出した必要ワード数 | スタック検査ヘルパ |
| `0xce`、`0xd0`、`0xd2`、`0xd4`–`0xda` | 各種の一時領域 | `LDC`、`SRS`、集合演算、呼び出し列 |
| `0x110` | 単調増加カウンタ。SIB の `Activity` に書かれる | セグメント切り替えヘルパ `0x10f5` |
| `0xe6` | **SYSCOM の基底であり、同時に `IORESULT`** | デバイス族、タスク切り替え |

`0x2270`–`0x227c` の 7 ワードは `ADR`、`SBR`、`MPR`、`DVR` だけが使う。浮動小数点
ルーチンのレジスタ退避領域で、この 4 本は `si`、`ax`、`bx`、`di` をまとめて `xchg` で
追い出し、あとで戻す。

## 一つの枠に二つの役目：`ss:0E6h`

`0x00E6` は SYSCOM（システム通信領域）の基底アドレスで、デバイス層はそこを構造体の
起点として扱う（@0x2B3B の `mov bp,0E6h` 以降、ずっと `[bp+1Ah]`、`[bp+2Ch]`）。
**同じワードが `IORESULT` でもある**——デバイス呼び出しは入口でそれを 0 に消し
（@0x2B3B の第 1 命令）、終わりに結果を書き戻す。

さらに上位バイトには第三の役目がある。タスク切り替え時に `MSPROC` と 1 ワードに
合成され、`TIB+12h` へ格納される（@0x160F の `mov ch, ss:0E6h`）。

**ここは噛みつく**：インタプリタがこの枠を書くのはタスク切り替えのときだけだ。
呼び出しのたびに書けば、デバイスの結果は次の帳簿づけに上書きされる——そして症状は
数千命令あとに、まったく別の顔をして現れる。

## 局所変数は空ではない

オリジナルは局所データを確保する前に、スタック検査ヘルパへ `call` する：

```
1045: mov ax, 3Ch
1048: cmp byte ptr ds:48h, 1
104d: je  1057
104f: call 02DAh          ; 戻り番地 1052h が旧 SP の下に積まれる
1052: jae 105Ah
1057: call 02DAh          ; こちらの戻り番地は 105Ah
105a: mov sp, ax          ; ヘルパが算出した新しいスタック頂点
```

この `call` は戻り番地を**旧 SP の 2 バイト下**に積む——そして局所データの確保が
終わると、その位置はちょうど**いちばん番号の大きい局所変数**になる。

つまり、ある手続きの最後の局所変数は最初から `1052h` あるいは `105Ah` を抱えている。
誰も気にしない些事に聞こえるが、OS の起動途中で `DATASIZE` が 1 の手続きが実際に
それを引数として渡す——**その値を再現しないと、40,619 番目の p-code で食い違う。**

## byte sex は推測ではない

枠 `0x44` はマニュアルに直接対応する。IV.0 の `MOV`（197）の定義にはこうある——
「UB が 2 で、当セグメントの byte sex がホストと逆のときは、転送時にワード単位で
バイトを入れ替える」。8086 版の `MOV`：

```
0a13: 0bed        or   bp, bp            ; UB
0a15: 7421        jz   通常の転送
0a17: 83fd02      cmp  bp, 2
0a1a: 7524        jnz  通常の転送
0a1c: 36833e440001 cmp word ptr ss:44h, 1
0a22: 741c        jz   通常の転送
0a24: ad          lodsw                  ; ワード単位で転送しつつバイト交換
0a25: 86c4        xchg al, ah
0a27: ab          stosw
0a28: e2fa        loop
```

`LDC`（131、オペランドは `UB_1, B, UB_2`）と `XJP`（214）も同じ判定を使う。
**`ss:44h` が 1 なら、そのセグメントの byte sex はホストと同じ。** この値は
セグメント切り替え時にコード・セグメント・ヘッダの `0x0c` バイト目から読まれる
（[セグメント切り替え](segment-switching.ja.md)参照）。

## エラーの出し方

実行時エラーはすべて同じ道を通る。エラー番号を `bp` に入れ、`0x020f` へ跳ぶ。

```
025a: bd0b00  mov bp, 11   ; 未実装命令。44 エントリがここを指す
0269: bd0e00  mov bp, 14   ; 0xff のみ
026e: bd1000  mov bp, 16   ; BPT
```

`0x40`–`0x5f`、`0xaa`、`0xaf`、`0xf5`–`0xfe` の 44 エントリはすべて `0x025a` を指す。
IV.0 マニュアルは `0xfa`–`0xff` を `RESERVE1`–`RESERVE6` としているが、この
インタプリタは最後の `0xff` をエラー 14 に振っている——**同じバージョン、同じ表で、
最後の 1 枠の割り当てだけが 68000 版と違う。**

## 境界

- 「使用者」欄は 169 本のディスパッチ先と 25 本のヘルパの逆アセンブルから数えたもので、
  逆アセンブル打ち切り以降は含まない。
- `0x3c` が指すのは現在タスクの TIB。版面は[マルチタスクとタスク切り替え](tasking.ja.md)
  を参照。`+04`／`+06`（スタックの上下限）は bootstrap が埋めるが、その算出方法は未解。
- `0xce` 以降の枠の用途は個々のハンドラから推定したもので、一貫した命名は無い。
